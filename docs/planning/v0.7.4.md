# v0.7.4 — Testability: Release Plan

**Theme:** Everything testable and tested — make the untested surface visible, bounded, and shrinking.
**Status:** Planning
**Milestone:** [v0.7.4 — Testability](https://github.com/thurlow-research/HumanOversightSystem/milestone/18)
**Inserted:** 2026-08-03, cascading v0.7.4→v0.7.6, v0.7.6→v0.7.8, v0.7.8→v0.7.10, v0.7.10→v0.7.12 (see [README](README.md))

## Theme rationale

HOS makes claims about code quality on other people's behalf. Those claims rest on its own oversight code — the gates, validators and authority modules that decide whether a human must approve. That code was, until this release, **substantially unmeasured and in one respect entirely unenforced**.

Three findings on 2026-08-03 set the scope:

1. **The test regime is an allowlist.** `[tool.coverage.run] source` names two directories and `[tool.mutmut] source_paths` one. Everything else is invisible by default, so **new code is born unmeasured**. 21 modules in `scripts/automation/lib/` and 7 `scripts/oversight/*_logic.py` had drifted outside it — not through neglect, but as the config's designed behaviour (#1174).
2. **Nothing runs the test suite.** No workflow invokes `pytest`; `scripts/framework/run_tests.sh` has zero callers. `fail_under = 80` has **never been enforced by any automated actor** (#1244).
3. **The gaps are in the worst places.** `scripts/oversight/signoff_gate.py` sits at **20%** and `scripts/framework/require_human_approval.py` at **48%** — the module deciding whether a human must approve is half unexercised. Aggregate coverage is 80%, so the mean hid the holes.

The same blind spot recurs wherever selection is keyed on a filename: `shellcheck.yml` selects `*.sh` and therefore never lints the six extension-less `bin/hos-*` launchers, including `hos-cron`, which runs both autonomous roles unattended (#1245).

**The theme is not "write more tests."** It is: *make the untested set enumerated, typed, owned, and monotonically shrinking* — because that is the only form of "everything is tested" a machine can check.

## The standard

"Zero exemptions" is not achievable: `bootstrap/hos_bootstrap.sh` installs the Python that would run its own test. Everything else is. The enforceable form, adopted as this release's standard:

> Nothing is excluded silently. Every exclusion is typed, justified, owned, and expiring, except two named bootstrap files. The exclusion list is a reviewable artifact, and the CI gate fails if reality drifts from it.

This is the **Ratchet Principle** (`research/findings/ratchet-principle.md`) applied to the test regime: the exempt set may shrink freely, and may only grow by explicit human decision.

| Action | Direction | Who |
|---|---|---|
| Remove an exemption / coverage rises | tightening | automated |
| Coverage drops below baseline | loosening | **blocked** |
| Add an exemption | loosening | **human approval** |
| New code below threshold | loosening | **blocked — no grandfathering for new code** |

## Open decisions

- [ ] **#1244** — ScottThurlow: do tests become a **required** check on autonomous-role PRs? It can block the worker/overseer merge loop on a flaky test with no human present. Recommended yes, with a documented `HOS_TESTS_REQUIRED=warn` escape hatch audited like `HOS_REQUIRE_TOOLS`, and suspension only via the human-authorized `gate-suspension.md` route. Advisory mode needs no decision and should ship regardless.
- [ ] **#1242** — approve the proposed ADR (deny-by-default inventory assertion, five exemption classes, risk-tiered floors, no kcov/bashcov) before implementation begins.
- [ ] Re-review **`signoff_gate.py`** and **`require_human_approval.py`**: prior sign-offs are not invalidated, but any coverage evidence cited in them was never real and must be re-derived.

## Completion condition

> Every first-party file is either measured against a floor with a ratchet, or carries a typed exemption with an owner, issue, and expiry; exactly two entries carry `expires: never`, both `bootstrap-paradox`; the count of non-permanent exemptions is published in the audit trail and is monotonically non-increasing; and a CI gate fails when any of these ceases to be true.

Stated as a number rather than an assertion, so "are we done?" has an answer.
