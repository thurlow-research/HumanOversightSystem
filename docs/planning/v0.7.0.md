## Scope principles (agreed 2026-10-25)

These principles, agreed by the human on 2026-10-25 and recorded on #2119, govern what is in v0.7.0 scope and supersede the original buckets below.

1. **Finish what we started.** "Started" means coding: code exists (merged in part, on an open PR, or on a branch with code). Land it. Spec-only work is deferred.
2. **Basic robustness and hardening that streamlines future workflow:** gates that report a pass without checking, cycle reliability (tokens, locks), the selector's view of work.
3. **Shippable:** the release mechanics work, or are explicitly waived for v0.7.0 by human ruling (release gates #1622–#1625, #1340; #2014 release cuts; #2137 consumer upgrade smoke test).
4. **Do no harm to consumers:** keep fixes for install/upgrade breakage and real security holes in shipped code (e.g. #2059, #2149). Low-severity defence-in-depth is deferred.
5. **Cut supervision friction:** the small set that makes the human the bottleneck (#2174, #2165, #2166, #2101, #2122, #2123, #2173).
6. **Defer by default:** new capability, research/measurement, docs that mislead no one, epics (keep only coded slices), and anything depending on later-release work. Deferrals go to an **even** release; odd releases (v0.7.1) are reserved for bug fixes after the preceding even release ships.
7. **Freeze scope** once the cut list is agreed: only critical bugs or security findings in v0.7.0's own code may enter afterwards. Everything else goes to v0.7.1 (post-release fixes) or an even release.

## Theme rationale

v0.5.0 makes HOS trustworthy. v0.7.0 makes it *self-improving*. Two sources of ideas: a systematic literature review (Cobb & Mills 1990 on statistical quality control; Poppendieck & Cusumano 2012 on lean) identified capabilities that flow naturally from HOS's architecture; and v0.4.0 field operation surfaced infrastructure reliability gaps resolved in v0.5.0. Both sets of insights land here once the v0.5.0 substrate is stable.

### Bucket 1 — SLR-Derived Quality Capabilities

**Why:** The literature gives us validated quality models; HOS's pipeline structure makes them implementable cheaply.

| Feature | Description | Issue(s) |
|---------|-------------|---------|
| MTTF/B-factor certification | B = MTTF_{n+1}/MTTF_n as consumer PR gate; release blocks if B < 1 | #563 |
| Usage-profile-weighted tests | Test distribution weighted by operational usage profile (Adams study: 21× more effective than coverage-first) | #564 |
| Lean waste report | Classify audit log cycle time into lean waste categories at each release | #565 |
| Quality ratchet | Defect density monotonically non-increasing across releases | #566 |
| Certification independence | System-test agent derives tests from spec, not from coder's coverage map | #568 |
