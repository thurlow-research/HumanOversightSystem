# Label registry

Single authoritative answer to "what does this label do, who writes it, and
where does its name live in code." Written per the #1349 ruling
(`DECISIONS.md`, 2026-09-06) as the "one authoritative place" for label
semantics. Doc-only — this registry does not itself change any control flow;
it records what the code (as of this writing) already does.

**Names are fixed literals, not configurable.** They are hardcoded across
`scripts/automation/lib/probe.py`, `bin/hos-cron`,
`scripts/framework/select_work_candidates.py`, `.github/workflows/label-swap.yml`,
and `scripts/automation/lib/merge_authority.py`. There is no runtime
label-name configuration anywhere in this repo — `scripts/framework/machine-accounts.env`
holds account identity and threshold config (`OVERSEER_CEILING`,
`HUMAN_REVIEWER`, `BOT_ACCOUNTS`) only, no label names. A consumer using a
different naming convention (e.g. `needs_ai` with an underscore) is
unsupported — do not attempt to detect or reconcile a local variant at
runtime.

**Pending rename.** Per the #1349 ruling (`DECISIONS.md`, 2026-09-06),
`needs-ai` is planned to be renamed to `needs-worker`, with a new
`needs-overseer` label introduced alongside it. That migration has **not**
happened yet — every row below reflects the current, pre-migration code as of
this writing. Do not treat `needs-worker`/`needs-overseer` as live; they are
not written or read anywhere yet.

## The `needs-ai` authorizing act (the durable reference home — #1540 S2, AM-27 point 1)

`scripts/framework/select_work_candidates.py` treats an issue's `needs-ai` label as a candidate for autonomous work only when its author is trusted (a CODEOWNER, a roster entry, or an HOS App identity: worker, overseer or human-proxy) **or** the label was applied by a verified individual human CODEOWNER, acting from their own GitHub account. A bot applying `needs-ai` to an issue authored outside the trusted set never authorizes it (AD-6). A `milestoned` event never authorizes anything, on any issue, regardless of title (AR-7): **the milestone loses the power to authorize, not the power to scope** — it still selects which issues the gate queries, but it confers no authorization weight, and the reason is structural, not merely operational: an untrusted issue can be milestoned by an automated sweep (Step 0) with no human act at all, so treating a milestone assignment as authorization would be a route around the gate a human never took.

1. **In the S2 era `/approve` changes no labels and authorizes nothing.** The command posts a comment naming the act that does authorize; it performs no `gh issue edit`.
2. **A label applied by `github-actions[bot]` is excluded by the gate** — which is *why* `/approve`'s label write was removed rather than merely reworded: the workflow token's actor is a bot, and a bot's label application never satisfies the gate, so leaving the write in place would have kept consuming a human's one genuinely additive act for zero benefit.
3. **What *does* authorize:** apply the `needs-ai` label to the issue from your **own** GitHub account (the web UI, the mobile app, or a personal-access-token `gh` invocation under your own login) — **never** `bootstrap/edit_issue.sh --app human`, which writes as `scottthurlow-claude[bot]` and does nothing, because the gate excludes bot actors unconditionally. **If the issue already carries the label**, GitHub's label writes are idempotent, so re-applying it produces no new event — remove it first, then re-add it, both from your own account. An `unlabeled` followed by a `labeled`, both by your own account, is **not** an undo-redo — it **is** the authorization record the gate reads.
4. **`/approve` cannot consume your additive act.** Earlier revisions of this gate let `/approve` apply `needs-ai` as `github-actions[bot]` even on an issue that did not yet carry the label, which silently spent the one act that would have authorized it. Making the command inert (no label write at all) removed that harm at its root, rather than merely rewording the confirmation message.
5. **A milestone assignment does not authorize anything** — not on a new issue, not on an old one, regardless of title. Do not remove-then-re-apply an issue's milestone as a way to "re-authorize" it; that act has no effect on the gate's determination and, on an unattended cron cycle, race against `bin/hos-cron`'s own Step 0 triage sweep (which assigns the active milestone to every milestone-less issue as `hos-worker-hos[bot]`) in a way that can consume the human's remaining acts on **both** channels.
6. **What the act does and does not do.** Applying `needs-ai` to an issue from your own account **starts autonomous work on that issue** — including an issue you did not author and whose content you do not control. It does **not** make the issue's author trusted, and it does **not** make the issue's body trustworthy: the gate never reads an issue's body or its labels as evidence of who filed it (FR5).

## Known gaps (not fixed by this registry)

- **No idempotent provisioning path.** `release-request`/`release-authorized`
  are two hand-run `gh label create` commands documented in a setup guide;
  the `hos-*` set is a list in a tech-design doc; `hos_install.sh` applies
  `needs-human` best-effort with a printed tip on failure. There is no single
  script that provisions every label in this table into a fresh consumer
  repo. Tracked as a follow-up from #1349.
- **No conformance test.** Nothing currently asserts that the label literals
  hardcoded in `probe.py`, `bin/hos-cron`, `select_work_candidates.py`,
  `label-swap.yml`, and `merge_authority.py` match this table, or that a
  label documented here as "informational" truly has no reader. Tracked as a
  follow-up from #1349.
- **The planned `needs-worker`/`needs-overseer` rename** (see "Pending
  rename" above) is not implemented. Migration scope — ~65 files touching
  `needs-ai` in live code, agent definitions, prompts, and tests; live
  GitHub issue relabeling; and a breaking-change story for at least one known
  consumer project running its own worker/overseer cron against the current
  convention — is tracked in a dedicated follow-up issue, not this one.
- **`scripts/framework/check_agents_static.sh`'s `KNOWN_LABELS` list** is a
  separate, narrower enumeration used only to validate agent-file escalation
  targets — it is not this registry and should not be treated as a second
  source of truth for label behaviour.
