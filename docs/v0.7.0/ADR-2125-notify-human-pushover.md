## 1. Organizing principle

The notifier is a **dumb, bounded, GitHub-free pipe with exactly one piece of memory**, its dedup record. Detectors decide **whether** to call it (REQ-14). The notifier decides only **whether this key was already sent**, and then **delivers or fails, in under 25 s, without leaking the credential**. Every failure is a non-zero exit with a fixed reason token. The caller owns what that failure means, and every designed caller treats it as `undelivered` and carries on. When the notifier has to choose between staying quiet and sending, it **sends**: a duplicate push is a nuisance, but a missing one is the outage this issue exists to prevent.

## 2. Decisions

### AD-1: Shape. A thin bash entry point over one stdlib-only Python module, run with `python3 -I`. (BINDING; REQ-1, REQ-3, REQ-5, the v0.7.4 shell-to-Python theme.)

- `bootstrap/notify_human.sh` is the **fixed path** that ADR-1605 AD-20, TD-1605 §15.7 and ADR-2100 AD-9 call. It does three things only:
  1. It resolves its own directory with `cd -P`.
  2. It checks that `python3` is on `PATH`. If it is not, it prints the AD-3 stdout line with `reason=no-python` and exits 4.
  3. It runs `exec env -u SSL_CERT_FILE -u SSL_CERT_DIR -u OPENSSL_CONF -u OPENSSL_MODULES -u OPENSSL_ENGINES python3 -I "<dir>/lib/notify_human.py" "$@"`. *(Amended round 1, security SF-6.)* The trust-store and OpenSSL-config variables are removed **before** the interpreter starts, because OpenSSL reads `OPENSSL_CONF` when `_hashlib` or `_ssl` first loads, which is earlier than any Python-side scrub can run. The module also deletes the same five names from `os.environ` as its first statement (belt and braces for a caller that bypasses the wrapper), and imports `ssl`, `hashlib` and `urllib.request` only after that.
  
  It reads no credential, no state and no environment value (unsetting is not reading), and has no `set -x`. *(Round 2, security NOTE, rejected.)* `LD_PRELOAD` and `LD_LIBRARY_PATH` are **not** added to the unset list. A preload is already loaded into the wrapper's own `bash` and into `env` before either can unset it, so the scrub would close nothing, and removing `LD_LIBRARY_PATH` can break a `python3` that legitimately depends on it, which would turn a hardening step into a silent channel. An actor who controls those variables also controls `PATH`, which the wrapper must honour to find `python3` (R-5). **Startup bound (NOTE-4, round 1):** the interval between the wrapper's start and the AD-6 watchdog's start (interpreter startup and stdlib imports) is bounded only by the caller's 30 s kill. That is accepted and documented in `docs/CRON-SETUP.md`. It follows `bootstrap/setup_clis.sh` style (`set -euo pipefail`, colour only when stderr is a TTY).
- `bootstrap/lib/notify_human.py` holds **all** of the decision logic: argument grammar, the cause table, credential parsing, the dedup record, transport, rendering and the audit call. It uses the **stdlib only** and supports Python 3.10 or later (the `hos_bootstrap.sh` floor). It is invoked by file path under `-I`, the same as `usage_pause.py` (`bin/hos-cron:461`). `-I` ignores `PYTHON*` variables and the user site directory, and keeps the script directory and the working directory off `sys.path`.
- **Why Python.** Every part of the job is decision logic or secret handling: closed-set validation, a credential file that must be parsed without being sourced, `fstat` ownership and mode checks, an `flock`-guarded record with an untrusted-state rule, TLS with verification, a bounded JSON response parse, and a hard wall-clock deadline. In bash, the credential would live in shell variables. Any `curl` invocation would be one flag away from AF-1, and the locking and parsing would be the hand-rolled shell logic that v0.7.4 is moving away from.
- **Why `bootstrap/lib/` and not `scripts/automation/lib/`.** The notifier must run under `-I` from a fixed bootstrap path, before auth, with no package import path. `bootstrap/lib/hos_tmp_root.py` is the precedent for a bootstrap-side stdlib module.
- **Why the AF-9 helpers are not imported.** `hos_tmp_root` is the tmp-root trust guard. Importing its private `_require_private_dir` would couple the notifier's semantics to a security module that changes for unrelated reasons. `usage_pause` is a 2,000-line module in `bin/lib/`. The checks needed here are about ten lines each. The TD names, at each use site, which existing function its check mirrors. That keeps the duplication declared (D41) without introducing a cross-module import.
- **Rejected alternatives:**
  - **(a) A pure bash script with `curl`.** Even with `--data @-` keeping the token out of argv, the token would still sit in shell variables, and the parsing and locking would still be shell decision logic.
  - **(b) Python that shells out to `curl`.** That adds a child process whose argv and environment are one mistake away from AF-1.
  - **(c) `requests`.** It is not stdlib, and the notifier must run before any venv is guaranteed.
  - **(d) A `-m scripts.automation...` module.** A package import cannot be resolved under `-I` from an arbitrary working directory.

### AD-2: The interface. A closed argument grammar and one cause table. (BINDING; REQ-1, REQ-2, REQ-11. ADR-1605 AC-40 and ADR-2100 AD-9 shapes accepted unchanged.)

- **Call shape:** `notify_human.sh --cause <id> (--issue <n> | --issue none | --url <u>) --since <iso> [--priority high|normal] [--body-file <path>] [--role <r>] [--project <p>]`. Separately, `notify_human.sh --test`, which takes no other argument.
- **The grammar is strict.** Each flag may appear at most once. An unknown flag, a missing value, a repeated flag, a positional argument, or `--test` combined with anything else is a usage error (exit 2).
  - `--issue <n>` must full-match `[1-9][0-9]{0,8}`.
  - `--since` must full-match `[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z` (AF-6) **and** parse as a real UTC datetime.
  - `--url` must full-match `https://github\.com/[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)+`, with at most 512 bytes. It must contain no `..` segment, no query, no fragment and no percent-encoding. Both ADR-1605 URL forms pass (AF-6). Everything else is rejected. The owner/repo in `--url` is **not** required to equal the resolved slug (security NOTE, round 1, rejected): a mismatch would be a usage error, which turns a mis-built caller URL into a lost push, and the URL is already confined to `github.com`.
  - *(Amended round 1, security SF-3.)* **Every grammar in this ADR (AD-2, AD-4, AD-7) is applied with `re.fullmatch` on the raw string**, never `re.match` with `$` (which matches before a trailing newline) and never `urlparse`/`startswith`. A static test pins that the module contains no `re.match(` and no pattern ending in `$`.
- **The cause table is a single module-level mapping** `CAUSES = {cause: priority}`, holding exactly the nine causes and priorities of REQ-2. Membership is the only check. `test` is not in the table. `--priority`, when given, must equal the table value, or the call is exit 2.
- **`--body-file`, under ESC-1 (B):** the flag is accepted and its value must be non-empty. **The file is never opened, read or checked for existence.** The notifier transmits nothing from it. This is a deliberate departure from REQ-4's "an unreadable `--body-file` is a usage error" (AM-1). If a non-zero exit came from an argument the notifier ignores, a caller whose temp body file could not be written would lose its push. That is silence caused by an unused input. Under ESC-1 (A), the file is read with a bounded, `O_NOFOLLOW` read of the first line only, and a failed read **degrades** to sending the push without the extra line. It never becomes an exit 2.
- **`--role` and `--project`** are optional and are never rejected for their charset (ADR-2100 AD-9 requires the call to be made even for a bad project key). Resolution is defined in AD-10, and rendering in AD-9.

### AD-3: Exit codes, one stdout line, and a fixed reason vocabulary. (BINDING; REQ-4. This is an interface pinned for every caller.)

- **Exit codes:**
  - **0**: `sent`, `deduped` or `test-sent`.
  - **2**: usage error, or an unpaired or invalid test override (AD-7).
  - **3**: credentials unavailable.
  - **4**: delivery failed. This includes a missing `python3`, a lock timeout and an internal error.
  
  No other code is used. Under ADR-1605's mapping (AF-6), a non-zero exit is recorded as `undelivered:exit-<N>`, so 2, 3 and 4 reach that caller's log line unchanged.
- **The stdout line.** On every exit, stdout carries **exactly one** ASCII line, matching:
  `^NOTIFY outcome=(sent|deduped|test-sent|failed) cause=([a-z][a-z-]{0,31}|test|-)( reason=[a-z][a-z-]{0,31})?$`
  `reason` is present if and only if `outcome=failed`. `cause=-` is used only when the call fails before the cause is validated. Nothing else is written to stdout. The human-readable detail goes to stderr, prefixed `notify_human:`. Any caller-supplied value echoed there goes through the AD-9 renderer first.
- **The reason vocabulary is closed.** The TD may add a token only by amending this list.

  | Exit | Tokens |
  |---|---|
  | 2 | `usage`, `test-override` |
  | 3 | `credentials-missing`, `credentials-insecure`, `credentials-malformed`, `home-mismatch` *(round 1, security SF-1)* |
  | 4 | `network`, `tls`, `http-4xx` (any 4xx except 429), `rate-limited` (429; *round 1, reliability SF-1*), `http-5xx`, `redirect`, `rejected` (a 2xx response whose `status` is not 1, or a body that does not parse), `timeout`, `deadline` (too little budget left to attempt a send; nothing was sent; *round 2, reliability NOTE-B*), `lock-timeout`, `recent-attempt` *(round 1, reliability MUST_FIX-2)*, `cooldown` *(round 1, reliability SF-1)*, `no-python`, `internal` |

  *(Amended rounds 1 and 2.)* Every token added in round 1 or round 2 maps onto an **existing** exit code (`deadline`, added in round 2, is exit 4): `home-mismatch` is a credentials-unavailable case (3), and `rate-limited`, `recent-attempt` and `cooldown` are delivery-not-made cases (4). No caller contract changes: ADR-1605 AD-20 and ADR-2100 AD-11 see `undelivered:exit-3` or `undelivered:exit-4` exactly as before. `recent-attempt` is deliberately **not** `deduped`, because after an ambiguous attempt the human may not have been told (AD-8).

- **Internal errors.** A top-level handler turns any unexpected exception into `reason=internal`, exit 4, and logs **only the exception class name** to stderr. It never logs the message or the traceback, because transport exceptions can embed request data. A static test pins that the module never calls `traceback.print_*` and never formats an exception object into output.
- *(Amended round 1, security SF-7.)* **Threads and hooks are covered too.** The AD-6 HTTP worker and the AD-11 audit worker each catch `BaseException` themselves and hand back a class-name token, never the exception object. At startup, before any thread exists, the module installs `sys.excepthook` and `threading.excepthook` replacements that print only `notify_human: internal <ClassName>`. A test raises inside the HTTP worker with a message containing a sentinel string and asserts that stderr does not contain it.
- *(Amended round 1, security NOTE.)* At startup the module sets `RLIMIT_CORE` to 0 (`resource.setrlimit`, best-effort), so a crash cannot write the in-memory token to a core file.

### AD-4: Credentials. The human's ruling, made mechanical. (BINDING; REQ-5. The location and format are the human's, 2026-10-20.)

- **Path.** `<passwd home>/.config/hos/pushover.env`, where the home is `pwd.getpwuid(os.getuid()).pw_dir`, as in `hos_tmp_root._home()`. It is **not** `$HOME`, and `XDG_CONFIG_HOME` is not consulted. The credential is the one input whose location a caller's environment should not be able to move. Every caller passes `HOME` (AD-20's allowlist), but a redirected `HOME` would let an environment writer route the human's pushes to a different Pushover account, which silently suppresses them. In normal cron use, the passwd home and `$HOME` are the same directory. The only redirect is the paired test override (AD-7).
- *(Amended round 1, security SF-1.)* **A `$HOME` that differs from the passwd home disables the default credential.** When the test override is **not** active, and `$HOME` is set, non-empty, and `os.path.realpath($HOME) != os.path.realpath(passwd home)`, the call exits 3 with `reason=home-mismatch` **before any state access, credential open or network call**. An unset or empty `$HOME` counts as equal. `$HOME` is still never used to locate the file, so this enables no redirect. Its purpose is test isolation: a test that sets `HOME=<tmp>` but forgets the AD-7 overrides (for example an `env -i` test or an explicit env dict in a `bin/hos-cron` test) now sends nothing instead of posting a real high-priority push from the production host. Production cron, systemd and interactive use have `HOME` equal to the passwd home and are unaffected. The check runs first so that the mismatched run also writes no dedup state. A TD test runs with `HOME=<tmp>` and no overrides and asserts exit 3 `home-mismatch`, no `os.open` of any credentials path and no connection. *(Round 2, security NOTE.)* The `docs/CRON-SETUP.md` troubleshooting row for `home-mismatch` names the two production shapes that hit it: `sudo -u <user>` without `-H` (which keeps the invoking user's `HOME`), and a container whose `HOME` (for example `/root`) differs from the passwd entry. The remedy is to run with a `HOME` equal to the passwd home.
- **Open and verify.** *(Amended round 1, security SF-8 and SF-4.)* The parent directory `<passwd home>/.config/hos` is opened with `O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC` and checked with `fstat`: it must be owned by `os.getuid()` and must not be group- or other-writable. The file is then opened **relative to that descriptor** (`dir_fd=`) with `O_RDONLY|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC`, and checked with `fstat` on the descriptor: it must be a regular file, owned by `os.getuid()`, with `mode & 0o077 == 0`, `st_nlink == 1` (a hard-link alias is refused), and no larger than 4096 bytes. A symlink at either level (`ELOOP` or `ENOTDIR`) or a failed check gives `credentials-insecure` and exit 3. The stderr line gives the `chmod 600` and `chown` remedy and never shows the content. A missing directory or file (`ENOENT`) gives `credentials-missing`. `docs/CRON-SETUP.md` adds a troubleshooting row: a dotfile manager that symlinks `~/.config/hos` or the file itself hits `credentials-insecure`, and the remedy is a real directory and a real file.
- **Parse, never source.** The content must be strict UTF-8 that is all ASCII. Lines are split with `split("\n")`, never `splitlines()` (security NOTE, round 1). A trailing `\r` is stripped from each line. Blank lines and lines whose first non-space character is `#` are ignored. Every other line must full-match `(PUSHOVER_TOKEN|PUSHOVER_USER)=("[A-Za-z0-9]{1,64}"|'[A-Za-z0-9]{1,64}'|[A-Za-z0-9]{1,64})`. One pair of matching quotes is tolerated because the human's ruling says "shell `KEY=value` lines". The following give `credentials-malformed`: any other key, a duplicate key, a missing key, an `export` prefix, and a value outside the charset. The message names the line number and the key, never the value. The charset check also guarantees that a value can carry nothing into the form body except itself.
- **Lifetime.** The two values live only in local variables of the send function. They are never placed in `os.environ`, never passed to `subprocess`, never stored on an object that is logged or rendered, and never written to the dedup record or the audit event.
- **Order.** *(Amended rounds 1 and 2.)* The full pre-send order is: argument validation → AD-7 override validation → the `home-mismatch` check → state open and per-key lock (AD-8) → dedup decision → ambiguous-attempt check (`recent-attempt`) → global cool-down check (`cooldown`) → credential read → minimum-budget check (`deadline`, AD-6) → attempt marker write → slug resolution (AD-9; **only** for `--issue <n>`) → send. The dedup, attempt and cool-down checks all run **before** the credential read, so a deduped, cooling or recently-attempted call needs no credential, runs no subprocess and makes no network call. *(Round 2, second review LOW.)* Slug resolution is **lazy**: round 1 ran it first, for every call, so a deduped, cooling, `--issue none`, `--url` or `--test` call paid a `git` subprocess (up to 3 s) for a value it never used. The slug feeds only the AD-9 message; neither the AD-8 key nor the AD-11 event uses it. It now runs only when a push for `--issue <n>` is about to be sent, after the marker is written, and its 3 s are counted in the minimum-budget check. A muted channel still reports `deduped` for keys already sent in the window. That is true: the human was told. The credential is read only when a send is about to happen, and everything after the watchdog starts runs inside the AD-6 deadline.
- **Muting.** Remove or rename the file. Callers then record `undelivered:exit-3` and carry on (REQ-13). There is no other mute switch, and no `HOS_*` variable can disable the channel short of the test override.
- **Sandbox.** The file is added to no sandbox allowlist (human ruling). Only unsandboxed processes read it.

### AD-5: Transport. In-process HTTPS with verification on, nothing in argv, no proxies, no redirects, a closed field set and no retries. (BINDING; REQ-5, REQ-7, REQ-10.)

- **Endpoint.** A module constant: `PUSHOVER_ENDPOINT = "https://api.pushover.net/1/messages.json"`.
- **Client.** `urllib.request`, using `ssl.create_default_context()` with system CAs and hostname checking on. A static test pins that the module contains no `CERT_NONE`, no `check_hostname = False`, no `_create_unverified_context`, and no `subprocess` call in the send path.
- *(Amended round 1, security SF-6.)* **The trust store cannot come from the environment.** `create_default_context()` honours `SSL_CERT_FILE` and `SSL_CERT_DIR`, and `python3 -I` does not strip them. An environment writer with DNS control could otherwise substitute a trust anchor and receive the real token, which is stronger than R-5's suppression class. The wrapper removes those names and the OpenSSL config names before the interpreter starts, and the module removes them again before importing `ssl` or `hashlib` (AD-1). A test runs the notifier with `SSL_CERT_FILE` pointing at a fixture CA and asserts that the fixture is not loaded. A static test pins the scrub list and its position before the first `ssl`/`hashlib` import.
- **Request.** A `POST` with a body from `urllib.parse.urlencode`, carrying a **closed field set**: `token`, `user`, `title`, `message`, `priority`. Nothing else is sent: no `retry`, `expire`, `sound`, `device`, `url` or `html`. The request also carries a fixed `User-Agent: hos-notify/1`.
- **Credential exposure.** The credentials travel only in the TLS-protected request body, built in memory. No process is spawned with them, so **AC-7's argv and child-environment property holds by construction**. The test still asserts it by recording every `subprocess` call made during a send (the only one is the AD-9 slug lookup) and checking its argv and environment.
- **Proxies are ignored.** The opener is built with `ProxyHandler({})`. AD-20's allowlist already strips `https_proxy`, so honouring it would make delivery depend on which caller ran the notifier. See ARCH-ESC-1 and R-4.
- **Redirects are refused.** A handler turns any 3xx into `reason=redirect`, so a request body is never replayed to another location.
- **Response.** At most 64 KiB is read. Then:
  - a 2xx response whose JSON object has the **integer** `status == 1` → `sent`;
  - any other 2xx → `rejected`;
  - 429 → `rate-limited` *(amended round 1; it was part of `http-4xx`)*;
  - any other 4xx → `http-4xx`, which includes an invalid token or user key;
  - 5xx → `http-5xx`;
  - a socket or DNS error → `network`;
  - an `ssl.SSLError` → `tls`.
  
  The response body is **never** printed or audited.
- **No retries inside a call.** The next occurrence retries. Dedup records only successes, and the AD-8 attempt marker and global cool-down bound how soon and how often that retry may reach the network (amended round 1).

### AD-6: A hard wall bound of 25 s on the whole process, enforced by a watchdog. (BINDING; REQ-7. ADR-1605 AD-20's 30 s bound and ADR-2100 AD-11's 120 s step. *Rewritten in round 1, reliability MUST_FIX-1.*)

The round-0 text bounded only the HTTP thread. The state-directory open, the lock and record I/O, the prune scan, the credential read, the `importlib` load of `cycle_log`, the audit write and the timeout path itself were all unbounded. Callers wait for **process exit** (command substitution, `timeout`, `subprocess.run`), not for the stdout line, so any of those could push a call past the caller's 30 s kill. The binding design is now:

- **The watchdog.** The first statements of `main()` (after the AD-1 environment scrub, the AD-3 excepthooks and the `RLIMIT_CORE` call, and **before argument parsing**) record `T0 = time.monotonic()` and start a **daemon watchdog thread** that sleeps until `T0 + WATCHDOG_SECONDS` (`25`). When it wakes it:
  1. acquires the **emit-once guard** (below) with a 0.5 s timeout. If it cannot (the main thread is stuck mid-emit on a blocked pipe), it skips to step 4 with the exit code the main thread had already selected, or 4 if none;
  2. if no stdout line has been emitted yet, emits `NOTIFY outcome=failed cause=<validated cause or -> reason=timeout`, and selects exit code 4;
  3. if a line **was** already emitted, keeps that line's exit code (so `sent` stays 0 even if the audit write then hung), and emits nothing more;
  4. *(Amended round 2, reliability NOTE-A.)* flushes stdout and stderr **only on the step-2 and step-3 branches, and only inside a short-lived daemon flush thread that the watchdog joins for at most `WATCHDOG_FLUSH_SECONDS` (0.5)**. Each flush is wrapped so an error cannot stop the exit. On the step-1 branch (the guard could not be taken, so the main thread is already blocked writing to the same pipe) the watchdog **does not flush at all**;
  5. calls `os._exit(<code>)` **unconditionally**, whatever the flush thread is doing.
  
  The stuck work (HTTP, audit, prune, a blocked `open`, a blocked flush) dies with the process, and every `flock` (AD-8) is released by the kernel. The watchdog is the **only** component allowed to decide the process ends early. Round 1 let the watchdog's own flush block on a stdout pipe the caller is not reading, so `os._exit` might never be reached, and with no `timeout` binary (AD-14) nothing outside would end the process. With the flush moved into a joined thread, the watchdog reaches `os._exit` within 25.5 s of `T0` on every branch, whatever the pipe does. The caller's `--kill-after` (AD-14) remains an outer bound, not the only one. A TD-H10 test holds stdout full (a caller that never reads) and asserts that the process exits within 25 s plus 1 s.
- **The emit-once guard.** Exactly one function writes the AD-3 stdout line. It holds a `threading.Lock`, sets a module flag and the chosen exit code, writes the line, and flushes. A second call is a no-op. This makes "exactly one stdout line" (AD-3) hold even when the watchdog and the main thread race at the deadline, and makes the line and the exit code always agree.
- **Every exit path flushes and then calls `os._exit`.** The normal end, a usage error, a credentials error, the internal-error handler and the watchdog all flush stdout and stderr explicitly and leave through `os._exit(code)`. None relies on interpreter shutdown, which can wait on non-daemon threads or block in a flush. A static test pins that the module has no `sys.exit` and no bare `return` out of `main()` that ends the process.
- **Sub-budgets.** Each is a named constant. The TD may lower a value but not raise it, and TD-H2 shows the sum:
  - `LOCK_WAIT_SECONDS` ≤ 5 (AD-8), polling every `LOCK_POLL_SECONDS` = 0.05 against a monotonic deadline;
  - `SLUG_SECONDS` ≤ 3 (AD-9);
  - HTTP: socket timeout ≤ 15 s, and the HTTP worker's `join` deadline is `max(0, min(15, T0 + 25 − now − POST_SEND_RESERVE))` (clamped at 0; *round 2, reliability NOTE-B*), where `POST_SEND_RESERVE` = 3 s covers the record rewrite (≤ 1 s, no `fsync`) and the audit join (≤ 2 s);
  - *(New in round 2, reliability NOTE-B.)* **Minimum send budget.** Immediately before the attempt marker is written, the main thread computes the time left, `T0 + 25 − now`. If that is less than `POST_SEND_RESERVE` + `MIN_HTTP_SECONDS` (2) + (`SLUG_SECONDS` when the target is `--issue <n>`, else 0), the call writes **no** marker, sends nothing, and ends `outcome=failed reason=deadline`, exit 4. `deadline` is a definitive no-delivery: it leaves the record unchanged and sets no global cool-down, because nothing about the endpoint was learned. Without this rule a call that reached the send late (a slow lock, a slow state directory) would write an ambiguous marker for a request that never ran, and the key would then be held off for 30 min by `recent-attempt` for no reason;
  - `AUDIT_JOIN_SECONDS` ≤ 2 (AD-11);
  - prune: runs only after the stdout line is emitted and only if at least 3 s remain, and stops at `T0 + 25 − 1`.
  
  Worst case without the watchdog: 5 (lock) + 3 (slug) + 15 (HTTP) + 1 (record) + 2 (audit) = 26 s. That is **deliberately** over 25, so the watchdog is the binding bound and the sub-budgets keep the common slow path below it. The caller's 30 s kill then has at least 5 s of margin over the watchdog.
- **Why a thread for HTTP.** A socket timeout bounds each socket operation, not the whole request, and a blocking `getaddrinfo` cannot be interrupted by a signal. So the HTTP call runs in a **daemon worker thread**, and the main thread waits on it with `join(<HTTP deadline>)`. When the join returns with the thread still alive, the main thread **re-checks the thread's result once** (reliability NOTE-2, round 1), so a send that completed exactly at the boundary is recorded as `sent`. Otherwise the outcome is `failed reason=timeout`: the line is emitted, the AD-8 attempt marker is **left in place** (the attempt is ambiguous; its `ambiguous` count was already raised when it was written, AD-8), the audit write is attempted under its own 2 s join, and the process exits 4.
- **The slug lookup's child process** runs with `start_new_session=True` and `stdin=DEVNULL`. On its 3 s timeout the notifier kills the **process group** (`os.killpg`), so a grandchild holding the pipe cannot block `communicate()` (reliability NOTE-3, security NOTE). The watchdog remains the backstop.
- **Proof obligation (TD-H10).** A test injects a blocking audit writer, and separately a blocking state-directory open, and asserts that the process exits within 25 s plus a small epsilon, with exactly one stdout line whose code matches the exit status.
- **No dependence on the environment around the call.** There is no prompt, no TTY, and no `$TMPDIR` or `/tmp` write anywhere in the notifier. The record lives in the state directory and the credential is read into memory. The notifier therefore works inside ADR-2100's dedicated alert `TMPDIR` and under a full `/tmp`.

### AD-7: Test overrides are paired, loopback-only, and can never carry the real credential. (BINDING; REQ-10, REQ-19, AC-8, AC-17.)

- **Two variables, both test-only:**
  - `HOS_NOTIFY_TEST_ENDPOINT`. It must be `http://127.0.0.1:<port>/<path>` or `http://[::1]:<port>/<path>`. These are IP literals only. `localhost` and every other host are refused, so no DNS lookup and no remote host is possible. `http` is allowed only here. *(Amended round 1, security SF-3.)* The check is `re.fullmatch(r"http://(127\.0\.0\.1|\[::1\]):([0-9]{1,5})(/[A-Za-z0-9._/-]{0,128})", raw)` on the raw string, with the port then required to be 1 to 65535. No `@`, `\`, `?`, `#`, `%` or whitespace can pass the pattern. The connection is made to the host and port **captured by that same match** (never re-parsed with `urlparse`). Negative tests pin at least `http://127.0.0.1@evil.example/`, `http://127.0.0.1.evil.example/`, `http://127.0.0.1:80\@evil.example/`, a trailing-newline form and `http://localhost:80/`.
  - `HOS_NOTIFY_TEST_CREDENTIALS`. A path to a credentials file, held to every AD-4 check.
  
  Neither name contains `TOKEN`, `SECRET`, `KEY` or `PASSWORD`, so AD-20's allowlist passes both to a caller's notifier under test.
- **Pairing.** If exactly one of the two is set, or the endpoint fails its grammar, the call exits 2 with `reason=test-override` **before** anything is read or sent. While the endpoint is overridden, the default credentials path is never opened (AC-8: the test asserts this by recording `os.open` calls).
- **The real credential cannot be smuggled in.** *(Amended round 1, security SF-4.)* The override file is opened and fully verified under AD-4 first (including `st_nlink == 1`). Then `fstat` of **that open descriptor** is compared, by `(st_dev, st_ino)`, against both `os.stat(default path)` (following a symlink, so a symlinked default is identified by its target) and `os.lstat(default path)`. Neither call opens the default file. A match on either exits 2 with `reason=test-override`. Comparing the already-open descriptor removes the path-versus-path race, and the `st_nlink == 1` rule removes the hard-link alias. Combined with the loopback-only endpoint, this means **no combination of `HOS_*` variables can send the real token anywhere but `api.pushover.net`**. The only remaining case is another local user listening on a loopback port, and they would still receive only a copied file, which only the owner can make.
- *(Amended round 1, security SF-5.)* **A leaked override cannot suppress real alerts.** While the overrides are active, the AD-8 state directory is `<state root>/notify-test/`, never `notify/`, so loopback "sends" never write or read the real dedup, attempt or cool-down records. Every overridden call writes `notify_human: WARN test override active` to stderr, and its audit event carries `mode=test-override` (AD-11). If the overrides leak into a crontab, real alerts go to loopback and are lost, but the audit log marks every one of them, and the real `notify/` state is untouched, so removing the leak restores delivery immediately with no 6 h shadow.
- **`--test` honours the overrides** (REQ-11), so AC-12 runs against the fake endpoint.
- **Session-wide test isolation (binding on S1's tests; ADR-2100 AD-10 pattern).** `tests/conftest.py` gains an autouse, session-wide fixture. It sets `HOS_NOTIFY_TEST_ENDPOINT` to a closed loopback port, sets `HOS_NOTIFY_TEST_CREDENTIALS` to a 0600 fixture file, and sets `HOS_STATE_DIR` to a per-session temp directory. As a result, **any** test that reaches the real notifier, including S2's and S3's `bin/hos-cron` tests and ADR-1605's and ADR-2100's caller tests, sends nowhere real and writes no real state. The notifier tests replace these with a live fake endpoint. A guard test asserts that the fixture is active.

### AD-8: The dedup record. One locked file per key, untrusted means absent, only a success suppresses, and an ambiguous attempt or a failing endpoint is rate-floored. (BINDING; REQ-6, AC-2, AC-3, AC-9. *Amended in round 1: reliability MUST_FIX-2, SF-1, SF-3, NOTE-1, NOTE-5; security SF-8, NOTE.*)

- **Directory.** The state root is `HOS_STATE_DIR` when it is set and non-empty, and `$HOME/.hos` otherwise. That is `bin/hos-cron:253`'s expression, mirrored from `usage_pause._state_dir`. The notifier uses `<state root>/notify/` (or `notify-test/` under the AD-7 overrides). `$HOME` is kept here, unlike AD-4, so that the notifier and `bin/hos-cron` agree on one state root. *(Amended round 1, security SF-8.)* Every state access goes through **directory descriptors**, never `lstat`-then-path:
  1. `<state root>` is created with mode 0700 if absent, then opened with `O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC` and checked with `fstat`: it must be owned by the current user. If it is group- or other-writable, those bits are removed with `fchmod` (the user owns it; `bin/hos-cron`'s `mkdir -p` may have created it under a `002` umask). It is **not** required to be 0700, because `bin/hos-cron` creates it with the ambient umask.
  2. `notify/` is created relative to that descriptor with mode 0700, opened the same way, and checked with `fstat`: a directory, owned by the current user, with group and other bits removed by `fchmod` if present.
  3. Every record open, read, rewrite, `unlink` and prune scan uses `dir_fd=<notify fd>` (`os.open`, `os.unlink`, `os.scandir(fd)`).
- **Three state tiers** *(amended round 1, reliability MUST_FIX-2 (b)).* The tier is recorded in the audit event's `state` field (AD-11).
  - **`ok`**: `notify/` is usable. Per-key records, as below.
  - **`fallback`**: the state root is usable but `notify/` is not (it is a symlink, a foreign directory or a file, or cannot be created). The notifier uses **one** file at a fixed name directly under the state root, `<state root>/notify-fallback.rec` (`notify-test-fallback.rec` under the overrides), opened with `dir_fd=<state root fd>` and `O_RDWR|O_CREAT|O_NOFOLLOW|O_CLOEXEC`, mode 0600, `flock`ed, and held to the same per-file trust checks. It holds a bounded JSON map of at most 64 per-key entries, `{<full key hash>: <record fields>}`, with the oldest `sent_at`/`attempt_at` entry evicted first, plus the reserved global cool-down entry. **Dedup, the attempt marker and the global cool-down all work unchanged in this tier**; only the storage moves. The stderr `WARN` names `notify/` as unusable. *(Amended round 2.)*
    - **The reserved cool-down entry is exempt from eviction** (reliability NOTE-D, security NOTE). It is not one of the 64, so a burst of distinct keys cannot evict a 429 cool-down and send the next 64 calls into a rate-limited endpoint.
    - **Its own size cap** (security NOTE). The round-1 "at most 1 KiB" rule is per-key and cannot apply to a 64-entry map. Fallback entries carry **only** the validated fields (`k` is the map key; no informational rendered fields), and the file is capped at `FALLBACK_MAX_BYTES` = 16 KiB. The TD pins, by test, that a full map (64 entries at maximum field widths plus the reserved entry) serialises to **at most half** that cap, so an over-cap file is never a legitimate full map. An over-cap or unparsable fallback file is untrusted and is **overwritten under the lock as an empty map** (the same rule as a per-key record that parses but is untrusted). It does not move the call to the `unusable` tier, so a corrupt file costs at most the dedup memory it held, never priority.
    - **A foreign-owned, symlinked or non-regular fallback file** (security NOTE) takes the per-key rule: the notifier unlinks it through `dir_fd=<state root fd>` (it owns the state root, and has just removed its group/other write bits) and retries the open once. Only if that fails does the call go to the `unusable` tier.
    - **The lock is not held through the HTTP call in this tier** (reliability SF-C). Unlike the `ok` tier, every key shares this one file, so round 1's "hold the lock through the send" made a slow Pushover serialise unrelated keys, and a concurrent different-key call (possibly high-priority) would end `lock-timeout` after 5 s. In the fallback tier the lock is therefore held twice, briefly: (1) for read, decision, and attempt-marker write, then **released** before slug resolution and the send; (2) re-taken, within the 1 s record reserve, for the final update, which **re-reads the map under the lock and changes only this key's entry and, if the outcome sets one, the reserved cool-down entry**, so no other key's concurrent update is lost. A concurrent same-key call during the send finds the fresh marker and ends `recent-attempt` (the R-2 contention-loser case). If the re-take fails within the 1 s reserve, the final update is skipped and the marker stays, which is the existing "send succeeded, record write failed" row of §3.
  - **`unusable`**: the state root itself is unusable, or the fallback file fails its checks. No state can be kept. The call **sends**, with no dedup, no marker and no cool-down, at the **stateless priority** `STATELESS_PRIORITY` = 0 (normal) in place of the cause's table priority, and writes `notify_human: WARN dedup state unusable (<class>); sending at normal priority` to stderr and `state=unusable` to the audit event. That still errs loud (ADR-1605 AD-18): the push is delivered. Downgrading to normal priority (which Pushover delivers but does not ring through quiet hours) is what keeps a stuck state directory from paging the human at night on every cron cycle. This downgrade is a product-visible architect decision and is routed to the human as **ARCH-ESC-3** (§8). The TD implements it as a named constant so that a ruling of "keep high" is a one-line change.
  - The worst-case push volume of each tier is stated in **R-2** (§4).
- **The key** is the NUL-joined UTF-8 bytes (surrogate-escaped) of the **raw** `(project, cause, target_kind, target, role if target_kind == "none" else "")`, where `target_kind` is `issue`, `url` or `none`. The file name is the first 32 hex characters of the key's SHA-256, plus `.rec`. Hashing makes a hostile project key path-inert. *(Amended round 1, security NOTE: the round-0 text mixed rendered and raw fields.)* The record stores the **full 64-hex SHA-256 of the raw key bytes** as `k`, and **that is the only match criterion**: a record whose `k` differs from the call's is treated as absent. The record may also carry the rendered fields for a human reading the file, but they are informational and are never compared.
- **Concurrency: the lock is on the record file itself.**
  1. Open `<hash>.rec` with `dir_fd=<notify fd>` and `O_RDWR|O_CREAT|O_NOFOLLOW|O_CLOEXEC`, mode 0600.
  2. Take `flock(LOCK_EX)`, polling with `LOCK_NB` and sleeping `LOCK_POLL_SECONDS` (0.05 s) between tries against a `time.monotonic()` deadline, never a busy spin (reliability SF-3), until the AD-6 lock budget runs out. On exhaustion, the notifier makes **one final lock-free read** of the record (reliability NOTE-5, adopted): if that read yields a trusted record with a fresh `sent_at`, the outcome is `deduped`, exit 0, because the winner has delivered. Otherwise the outcome is `reason=lock-timeout`, exit 4. A torn read during the winner's rewrite does not parse and simply falls through to `lock-timeout`.
  3. Once locked, re-verify that `fstat(fd)` has `st_nlink >= 1` and the same `(st_dev, st_ino)` as `os.stat(<name>, dir_fd=<notify fd>, follow_symlinks=False)`. If either check fails, a prune unlinked the file between steps 1 and 2. Reopen and retry, at most three times. *(Amended round 1, reliability SF-3.)* **When the three retries are exhausted, the key is treated as untrusted and the call takes the untrusted path below** (the fallback map, or failing that a send with no lock or record and `state=untrusted`). It is never `lock-timeout` and never a silent exit, because a race that keeps unlinking the file is untrusted state, and untrusted state sends.
  4. Read the record and decide (below). On a send, **write the attempt marker, then keep the lock held through the HTTP call**, and afterwards rewrite the record **in place** (`ftruncate`, `write`) under the same lock. (This holding rule is for the `ok` tier's per-key files, where no other key shares the lock. The `fallback` tier's shared file releases the lock across the send; see the tier list above. *Round 2, reliability SF-C.*) *(Amended round 1, reliability NOTE-1.)* There is **no `fsync`**: a record lost to a crash only produces a duplicate push, which R-2 already accepts, while `fsync` is the one call that could overrun the 1 s record reserve on a slow disk.
  
  Two concurrent same-key calls therefore send at most once. Different keys never contend. A torn in-place write does not parse, so it counts as absent and the next call sends (fail loud). Rename-based atomic replacement is **rejected** here because it would separate the lock from the inode that later callers open.
- **Record format.** *(Amended round 1.)* JSON with `{"v": 2, "k": <64-hex key hash>, "sent_at": <int epoch or null>, "attempt_at": <int epoch or null>, "ambiguous": <int 0..16>}`, plus optional informational rendered fields, at most 1 KiB, validated field by field. `v` is 2 because nothing has shipped at `v: 1`; a `v: 1` record is treated as absent.
- **The attempt marker** *(new in round 1, reliability MUST_FIX-2 (a)).* A `timeout` is **ambiguous**: Pushover may have accepted the message. Round 0 wrote nothing on a timeout, so a slow-but-accepting Pushover produced a high-priority duplicate on every cron cycle for as long as it stayed slow. The rule is now:
  1. Immediately before the HTTP call, still under the lock, the record is rewritten with `attempt_at = now` **and `ambiguous = min(ambiguous + 1, 16)`** (keeping any old `sent_at`). *(Amended round 2, second review MEDIUM.)* The count is raised **when the marker is written**, not after a timeout, so every way an attempt can end ambiguously (a normal `timeout`, the watchdog firing mid-send, a crash, a caller kill) carries the doubled back-off. Round 1 raised it only on the main thread's normal `timeout` path, so a send that kept ending by watchdog or kill stayed at the 30 min base indefinitely. This also removes the second record write the round-1 timeout path needed.
  2. On `sent`: `sent_at = now`, `attempt_at = null`, `ambiguous = 0`.
  3. On a **definitive** failure, meaning one where the request certainly did not produce a delivery (`network`, `tls`, `redirect`, `http-4xx`, `rate-limited`, `http-5xx`, `rejected`): `attempt_at = null`, `ambiguous = 0`. The next occurrence retries normally (subject to the global cool-down). (`deadline` never reaches step 1, so it writes nothing.)
  4. On an **ambiguous** end (`timeout`; the watchdog firing mid-send; a crash or kill after step 1; or a `sent` whose record rewrite then failed): the marker, with the count step 1 already raised, stays as written. Nothing further is written on this path.
  5. **Decision rule.** A trusted record whose `attempt_at` is younger than the ambiguous cool-down gives `outcome=failed reason=recent-attempt`, exit 4: no credential read, no network call. The cool-down is `ATTEMPT_COOLDOWN_BASE_SECONDS` (1800) × 2^(max(ambiguous, 1) − 1), capped at `DEDUP_WINDOW_SECONDS`. Because step 1 raises the count before each attempt, the first ambiguous attempt carries `ambiguous = 1`, so the schedule is 30 min, 1 h, 2 h, 4 h, then 6 h, unchanged from round 1 and R-2. It is `failed`, never `deduped`, because the human may not have been told. Callers record `undelivered`, which is true as far as the notifier knows.
  6. `attempt_at` in the future by more than 300 s makes the record untrusted, as for `sent_at`.
- **The global failure cool-down** *(new in round 1, reliability SF-1).* If Pushover is down or hung, round 0 made every call from every project and role pay up to 25 s on the pre-auth cycle path. Now a single fixed-name file `<notify dir>/_global.cooldown` (outside the `*.rec` prune glob; held to the per-file trust checks; written under a non-blocking `flock`, skipped if busy) holds `{"v": 1, "until": <int epoch>, "reason": <AD-3 token>}`.
  - It is written after `network`, `timeout` or `http-5xx` with `until = now + FAILURE_COOLDOWN_SECONDS` (300), and after `rate-limited` with `until = now + RATE_LIMIT_COOLDOWN_SECONDS` (3600), because retrying a quota 429 within minutes is useless.
  - It is **not** written after `tls`, `http-4xx`, `redirect` or `rejected`. Those are configuration faults that the human must see on every call, and they cost no time.
  - A call that is not deduped and not recently attempted, and finds a trusted `until` in the future, ends `outcome=failed reason=cooldown`, exit 4, with no credential read and no network call. stderr names the reason that set the cool-down. A `--test` call **ignores** the cool-down, so the human can always check the channel by hand.
  - An untrusted or unreadable cool-down file is treated as absent, so the call goes to the network. That errs loud.
  - *(New in round 2, reliability SF-A and security SF-10.)* **`until` is bounded, like `sent_at` and `attempt_at`.** A cool-down is untrusted (absent) when **any** of these holds:
    - `reason` is not one of the four tokens that set a cool-down (`network`, `timeout`, `http-5xx`, `rate-limited`);
    - `until − now > RATE_LIMIT_COOLDOWN_SECONDS + 300` (3900 s), the absolute ceiling whatever the reason says;
    - `until − now >` the cool-down that its recorded `reason` sets, plus 300 s (so 600 s for `network`/`timeout`/`http-5xx`, 3900 s for `rate-limited`).
    
    Round 1 bounded only the per-key times, yet the cool-down has the **wider** blast radius: one forged or corrupt `until`, or a value written while the clock was stepped forward and then corrected, would fail every call of every project and role with `cooldown`, with no network attempt, for as long as `until` stayed ahead of the clock, including a genuine new high-priority cause. With the bound, the longest a bad value can hold the channel shut is 65 min (a well-formed `rate-limited` entry), and a clock correction is absorbed within the 300 s slack. An untrusted cool-down is simply overwritten by the next outcome that sets one. The same three rules apply to the fallback map's reserved entry and to `notify-test/_global.cooldown` under the AD-7 overrides. A TD test plants a far-future `until`, and one whose `until` exceeds its reason's period, and asserts that each call goes to the network.
  - In the `unusable` tier there is no cool-down. In the `fallback` tier the cool-down lives in the fallback map under the reserved entry, exempt from eviction.
- **Untrusted means absent** (ADR-2100 AD-11 rule). The record is treated as absent if it:
  - is a symlink (`ELOOP` on open);
  - is not a regular file;
  - is owned by another user, or has group or other bits set;
  - is oversized or does not parse;
  - has a missing or wrong-typed field, or a `v` other than 2;
  - has a `k` that does not match the call's key hash;
  - has `sent_at` or `attempt_at` in the future by more than 300 s, so that a forged far-future time cannot suppress the key indefinitely (the global cool-down's `until` has its own bound, above; *round 2*).
  
  A record that parses but is untrusted is overwritten under the lock like an absent one. If the path cannot be opened or locked because of what is there (a symlink, a foreign file, a directory), the notifier unlinks it (it owns the 0700 directory) and retries once. *(Amended round 1, reliability MUST_FIX-2 (b) and SF-3.)* If that fails, or the step-3 retries are exhausted, **this key** moves to the `fallback` tier for this call (the fallback map holds its dedup, marker and cool-down). Only if the fallback is also unusable does the call send with no lock and no record, at `STATELESS_PRIORITY`, with `state=untrusted` in the audit event. A per-key fault therefore cannot become an every-cycle high-priority storm while the state root is usable. The at-most-once guarantee holds only while some state is usable, which is exactly REQ-6's qualifier.
- **Decision** *(amended round 1)*, applied in this order under the lock:
  1. a trusted record with `now - sent_at < DEDUP_WINDOW_SECONDS` (`6 * 3600`, a named constant) → `deduped`, exit 0;
  2. a trusted record with an `attempt_at` inside the ambiguous cool-down → `recent-attempt`, exit 4;
  3. a trusted global cool-down in force → `cooldown`, exit 4;
  4. otherwise → read the credential, apply the AD-6 minimum-budget check (`deadline`, exit 4, nothing written, if too little time is left), write the attempt marker, resolve the slug if the target is `--issue <n>` (AD-9), and send.
  
  None of steps 1 to 3 reads the credential or touches the network. Only `sent` sets `sent_at`, so only a success suppresses a key for the window. Failures update only the marker fields, as above. A credentials failure (exit 3) happens before the marker is written and leaves the record unchanged. `--test` reads and writes no per-key record and ignores the global cool-down, but a `--test` failure that would set the cool-down does set it.
- **Bounded growth.** Each call prunes opportunistically, **after** the stdout line has been emitted and flushed (AD-6), so a slow scan can delay only the exit, never the outcome, and the watchdog still bounds it. It removes up to 200 `*.rec` entries (through `os.scandir(<notify fd>)`) whose `mtime` is older than twice the window, taking `LOCK_EX|LOCK_NB` on each and re-verifying it before unlinking. An entry that is locked is skipped. Pruning is best-effort: its errors are ignored, it runs only if at least 3 s of the budget remain, and it stops at `T0 + 24 s`. The fallback map is bounded by its 64-entry cap (the reserved cool-down entry is not counted and never evicted) and its 16 KiB file cap.

### AD-9: The message. A fixed template, a locally resolved link, one renderer and named priorities. (BINDING; REQ-3, REQ-8, REQ-9. ADR-2100 AD-9's pointer-only rule, applied to every cause. ADR-1944 A6-4.)

- **Title.** The constant `HOS help`.
- **Message.** `HOS help: <cause> [<project>/<role>] — <target> — waiting since <since>`, all on one line. `<target>` is one of:
  - for `--issue <n>`: `https://github.com/<slug>/issues/<n>` (GitHub redirects that path to a PR when `<n>` is one), or `#<n>` when no slug resolves;
  - for `--url`: the validated URL, unchanged;
  - for `--issue none`: the constant `no GitHub item; see the cron log for this role`.
  
  The message never contains a path, a host name, a credential, an environment value, GitHub text, or anything from the body file (ESC-1 (B)).
- **ADR-2100 consistency.** AD-9 of ADR-2100 asks for the fixed constant "GitHub item could not be filed; see the cron log for this role" when `issue=none`. Under ESC-1 (B), the notifier supplies its own `issue=none` constant. The wording differs, but it meets the rule as written: a fixed constant with no variable detail. ADR-2100 S2 needs no change, and its body file is accepted and ignored (AD-2).
- **Slug resolution, local only, and lazy** *(round 2)*. It runs only for an `--issue <n>` target, and only once a push is about to be sent (AD-4 order); a deduped, cooling, recently-attempted, `--issue none`, `--url` or `--test` call never runs it. The slug comes from `HOS_REPO_SLUG`, if set and it full-matches `merge_config._REPO_SLUG_RE` (`^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$`). Otherwise the notifier runs `git -C <clone> remote get-url origin` with `timeout=3` and a minimal environment (`PATH` and `HOME` only), and parses the result with **the same rules as `merge_config.resolve_repo_slug`**. A **parity test** runs both parsers over a fixture set of remote URLs and asserts identical results, so the copy cannot drift (AF-8, declared D41 duplication). `<clone>` is the notifier file's own repository root (`Path(__file__).resolve().parents[2]`). Any failure falls back to `#<n>` and is still sent (REQ-3).
- **One renderer** (REQ-9) for every caller-supplied value the notifier transmits or echoes, other than `--issue`, `--since` and `--url`, which are validated instead. Today that is `role` and `project`, plus the body line under ESC-1 (A). The renderer works on raw bytes:
  1. it keeps only the first line;
  2. it maps each byte outside `[A-Za-z0-9 ._,:;=()+-]` to `?`;
  3. it caps the result at 64 characters for role and project, and 200 for a body line, with `...` marking a cut.
  
  The allowlist excludes `/`, `~`, `\`, `<`, `>`, `@`, the backtick, `#`, and every control or non-ASCII byte. An empty result renders as `unknown`.
- **Priorities.** `HOS_PUSHOVER_PRIORITY_HIGH = 1` and `HOS_PUSHOVER_PRIORITY_NORMAL = 0`, which mirror ADR-1944's `hos_pushover_priority_high` and `hos_pushover_priority_normal`. If H-9 on #1944 changes them, both places change together, and the S1 PR body records that coupling. A static test pins that no priority value other than 0 and 1 is reachable, so emergency (2) is never sent. *(Amended round 1.)* The priority sent is the cause's table value, except in the AD-8 `unusable`/`untrusted` stateless case, where it is `STATELESS_PRIORITY` (0, pending ARCH-ESC-3). The audit event records the priority actually sent.
- **Limits.** The message is at most 1024 characters by construction: the template plus 64 + 64 + 512 + 20 fixed fields comes to about 750. A test pins the worst case.

### AD-10: Role and project resolution, and one new export from `bin/hos-cron`. (BINDING; REQ-1, VF-7, AF-7. ADR-2100 AD-9 needs role and project on the push.)

- **Resolution order:**
  - role: `--role`, then `HOS_CYCLE_ROLE`, then `unknown`;
  - project: `--project`, then **`HOS_CYCLE_PROJECT`**, then `unknown`.
  
  The value is never rejected. It is rendered (AD-9) for the message and the audit event, and used raw (hashed) in the key (AD-8).
- **S1 adds one line to `bin/hos-cron`**, directly after `:365`: `HOS_CYCLE_PROJECT="$PROJECT"`, added to the same `export`. The raw key is used, not `_project_safe`, because the notifier renders it itself. This belongs in **S1**, not S2. ADR-2100 S2 and ADR-1605 Part 3 call with the AC-40 shape, which has no `--project`. Without the export, every project on the machine would render, and dedup, as `unknown`. That is a cross-project suppression bug on the very first cross-issue call. `HOS_CYCLE_PROJECT` contains none of the excluded words, so AD-20's allowlist already passes it.

### AD-11: Audit. `human-notified` through the existing writer. It never changes the exit code. (BINDING; REQ-12, AF-3.)

- **The existing writer is reused.** `scripts/automation/lib/cycle_log.py` is loaded **by file path** with `importlib`, from the notifier's own clone (`parents[2]`), which is the same technique `cycle_log` uses to load `audit_log`. The notifier calls `log_event("human-notified", ...)`. The record lands in that clone's `audit/log/`. If the file is absent (an unusual consumer layout), or the import or write raises, the notifier writes a single stderr `WARN`, and the exit code and stdout line are unchanged.
- *(Amended round 1, reliability MUST_FIX-1.)* **The audit write is bounded.** The `importlib` load and the `log_event` call run together in a **daemon audit thread**, which the main thread joins for at most `AUDIT_JOIN_SECONDS` (2). If the join times out, the main thread writes `notify_human: WARN audit write timed out` to stderr and proceeds to exit with the code already chosen. A hang in the import (working-tree code) or on a slow disk therefore costs at most 2 s, and the AD-6 watchdog bounds even that.
- *(Amended round 1, security SF-2 (c).)* **Late import.** `cycle_log` and `audit_log` are imported only in the audit thread, which starts **after the send function has returned** and after the main thread has dropped every reference to the credential values (the send function's locals are gone, and the parsed values are never stored outside it). A static test pins that no module-level import of `cycle_log` or `audit_log` exists and that the import site is reached only after the send path. This is defence in depth, not a guarantee: CPython cannot zero a `str`, so the values may still be in freed memory that working-tree code running in the same process could scan, and on the `timeout` path the stuck HTTP worker still holds them in its frame while the audit thread runs. R-1 records that.
- **Fields:** `role` (always passed, AF-3), `project` (rendered), `cause` (or `test`), `target_kind`, `target` (the issue number, the validated URL, or `none`), `priority` (the value actually sent, AD-9), `outcome`, `reason` (only when `failed`), `state` (`ok`, `fallback`, `unusable` or `untrusted`; present when the dedup state was not `ok`; *`fallback` added in round 1*), and `mode` (`test-override`; present only when the AD-7 overrides are active; *added in round 1, security SF-5*). These are the AD-3 tokens.
- **Never in the event:** a credential, the message text, body-file content or path, the credentials path, the state path, or a host name.
- **Coverage.** Every call that passes argument validation writes exactly one event, and `--test` writes one with `outcome=test-sent` or `outcome=failed`. A usage error (exit 2) writes none. It has no validated cause to record, and the caller already records `undelivered:exit-2`.
- **Timing.** *(Corrected in round 1, reliability MUST_FIX-1.)* The audit write happens after the stdout line is written and flushed. Round 0 claimed that this alone stopped a slow disk from turning a `sent` into a caller-side timeout. **That was wrong:** callers wait for process exit, not for the line. What actually bounds it is the 2 s audit join plus the AD-6 watchdog. Writing the line first still matters for a different reason: the outcome and the exit code are fixed before any slow work starts, so a watchdog exit during the audit write reports the true outcome (`sent` stays exit 0) rather than `timeout`.

### AD-14: Trigger architecture for S2 and S3. (DIRECTION. It binds the S2 and S3 TDs once ESC-2, ESC-3 and ESC-4 are ruled. It does not bind S1.)

- **Counters live in Python, not bash.** A new `bin/lib/notify_triggers.py` holds the pure counter logic: increment, reset, threshold and the `--since` bookkeeping. Its state lives under `$_HOS_DIR/notify-trigger/<role>-<project-hash>.json`. Its I/O is injectable, it runs as `python3 -I`, and it uses the AD-8 untrusted-state checks. `bin/hos-cron` only calls it and acts on a one-line verdict.
- **Untrusted or unusable counter state is treated as "threshold reached"** for the **high-priority** S2 causes, and the call is made. That errs loud, and AD-8's dedup (or, with the state root unusable, AD-8's stateless priority downgrade) bounds the noise. *(Amended round 1, reliability SF-4.)* For the **normal-priority** counter cause (`worker-idle`, S3a), unusable or untrusted counter state means **no call**, with the cycle log line carrying `alert=skipped:counter-state-unusable`. Otherwise an unusable `~/.hos` would fire `worker-idle` on the first `eligible=0` cycle and, with dedup unusable in the same directory, on every cycle after. The S3a TD records this choice (AM-8). A worker-idle condition that coincides with an unusable state root is not lost: the high-priority S2 causes and the cycle log still surface the state fault.
- **Every `bin/hos-cron` notifier call** goes through one shell helper. That helper:
  - uses `env -i` plus AD-20's allowlist;
  - *(amended round 1, reliability SF-2)* applies `timeout --kill-after=2 30` (or `gtimeout`), resolved once with the `_UP_BOUND` idiom (`:432-437`). When neither binary exists the helper runs the notifier unbounded by the shell, and the AD-6 in-process watchdog (25 s, after interpreter startup) is then the **only** bound. The S2 TD and `docs/CRON-SETUP.md` say so;
  - passes explicit `--role` and `--project`;
  - *(amended round 1, security SF-9)* derives the appended `alert=<sent|deduped|undelivered:<reason>>` **only** from the exit code and from the notifier's stdout after it has fully matched the AD-3 regex (under `LC_ALL=C`, as `_UP_VERDICT_RE` is matched). A non-matching stdout is logged as `undelivered:exit-<N>` and never interpolated (CWE-117);
  - *(amended round 1, reliability SF-2; **rewritten round 2**, second review HIGH and reliability SF-B)* applies a **per-cycle cap on network-capable calls, not on calls**, for the #2125-owned triggers. Round 1 capped every invocation at one per cycle, so a trigger whose condition persists (for example `worker-idle`, deduped for 6 h) took the only slot every cycle with a millisecond `deduped` call, and a later trigger (`needs-human-stale`) was skipped with `alert=skipped:cycle-cap` on **every** cycle, indefinitely. The binding rule is now:
    1. **Cheap verdicts never take the slot.** After each call the helper classifies the result, using only the exit code and a fully-matched AD-3 line (the SF-9 rule). A result is **cheap** if and only if it is one of: exit 0 with `outcome=deduped`; exit 4 with `reason=recent-attempt` or `reason=cooldown`; exit 3 (any reason); exit 2 (any reason). By the AD-4 order, every cheap verdict is reached **before** the attempt marker, the slug subprocess and any network I/O, so each costs interpreter start plus a few file operations. A cheap verdict sets nothing, and the next trigger in the cycle is called normally.
    2. **Everything else takes the slot**: `sent`, every other exit-4 reason (including `timeout`, `deadline` and `lock-timeout`), an exit status outside {0, 2, 3, 4}, a `timeout` kill, and any stdout that does not fully match the AD-3 regex. These are the results that can carry the 25 s network or watchdog cost.
    3. Before each call the helper checks two things. If the slot is taken, the trigger is not called and the log line carries `alert=skipped:cycle-cap`. If the wall time already spent on #2125-owned calls in this cycle is at least `NOTIFY_UNCHARGED_BUDGET_SECONDS` (10), the trigger is not called and the log line carries `alert=skipped:cycle-budget`. In both cases the trigger's counter is **not** reset, so it is offered again on the next cycle.
    
    **What this guarantees.** A cheap outcome cannot starve another trigger through the slot, because it never takes the slot. It could exclude one through the budget only if the cycle's cheap calls together took 10 s or more. That does not happen in normal operation: a cheap call is well under 1 s, and the one slow cheap path (waiting up to 5 s on a same-key lock) needs a concurrent caller of the same key, which the cron lock rules out for this role and project's own triggers (the keys of `--issue none` causes include the role, AD-8), leaving only an occasional interactive or cross-issue caller. The budget is a backstop against a pathologically slow state directory, and its skip has its own log token so it is visible, never silent. In agy's case, `worker-idle` and `needs-human-stale` both active and both deduped, both are called every cycle, both return `deduped`, and neither is skipped. **Order:** the fixed sites run first, in code order (`cron-lock-stuck`, `usage-pause-fail-closed`, `token-mint-failed`, then `worker-idle`), and S3b's per-item calls run last. The S3b TD must show that its expected per-cycle item count keeps the expected cheap cost below half the budget, or else cap the items per cycle and rotate which items go first.
    
    **The bound.** At most one charged call, plus the cheap calls started before the 10 s budget ran out. Every call is limited to 32 s by the helper's `timeout --kill-after=2 30` (with no `timeout` binary, by the AD-6 watchdog at 25.5 s after interpreter start, as stated above), so the worst case for #2125-owned calls is **42 s per cycle** (10 s of cheap calls, then one call of up to 32 s). That replaces round 1's 32 s figure. In normal operation it stays at 32 s plus well under a second per cheap call. The **push** ceiling does not change: a push is `sent`, which takes the slot, so there is still at most one #2125-owned push per role and project per cycle (R-2). The cross-issue calls (ADR-2100's alert step inside its own 120 s cap, and ADR-1605's `check_error` call under AD-20's 30 s) keep their own merged budgets and are not counted against this cap or this budget.
    
    **Rejected: a caller-side memo** (agy's alternative), in which `notify_triggers.py` stops calling for 6 h after a `sent` or `deduped` verdict. That would be a second dedup clock beside AD-8's. If the notifier's state were lost or reset (for example the human clears `~/.hos/notify/` to force a resend), the memo would still suppress the call, so the alert would be silent. The notifier is the one owner of "was the human told".
  
  It never changes the cycle's exit code.
- **`cron-lock-stuck` (S2):**
  - The call is made by the process that observes `age ≥ ceiling` (`:321`), **once**, whether or not its own `mkdir` then succeeds. The "could not acquire after reclaim" branch (`:324`) is the same event seen by the same process, not a second trigger. (AM-5)
  - *(Amended round 1, reliability SF-2.)* **Placement:** the call is made **after** the lock acquire-or-fail decision, never between the stale-lock `rm -rf` and the `mkdir`, so a 30 s notifier cannot widen the reclaim race window. On the acquired branch it follows the `pid` write and the `EXIT` trap; on the failed branch it precedes that branch's `exit 0`.
  - *(Amended round 1, reliability MUST_FIX-2 (b), worst-case analysis.)* **A missing lock directory is not a stuck lock.** Today `_stat_mtime` prints `0` when the lock directory cannot be stat'ed, so a `mkdir` that fails because `~/.hos` is read-only or full computes an age of about 56 years and takes the reclaim branch on every cycle. S2 must trigger only when the lock directory **exists** and its mtime was read successfully (a non-zero value). Otherwise an unusable state root would page `cron-lock-stuck` on every cycle of every role and project, which is exactly the correlated storm R-2 bounds.
  - A dead-PID reclaim (`:331-334`) is not a trigger.
  - The call precedes `_audit` and `HOS_CYCLE_*` (AF-7), so it passes `--role "$ROLE" --project "$PROJECT"`.
  - S2's TD must state that a legitimately long cycle under a disabled cap (`HOS_CRON_MAX_SECONDS=0`, ceiling 3600 s) is now paged at high priority. That is today's reclaim, made visible, and it is disclosed rather than suppressed.
- **`token-mint-failed` and `usage-pause-fail-closed` (S2)** use the K-consecutive counter of ESC-2. The usage gate's pause path `exit 0`s at `:481`, so the call must come before that exit. `pause/limit` never counts.
- **`worker-idle` (S3a)** reads the selector's existing summary line (`select_work_candidates.py:785-795`) and does not recompute eligibility. *(Round 2, reconciled with REQ-16 as clarified in `53635c38a`.)* The counter rule is REQ-16's, and this ADR does not restate a different one: a cycle with `eligible=0 complete=no` (selector exit 3) **increments** the counter whatever `scanned` reports, including `scanned=0`; `scanned=0` **resets** it only with `complete=yes`; `eligible>0` resets it; cycles that never reach the selector do neither. The S3a TD pins both `scanned=0` cases (AC-15).
- **`needs-human-stale` (S3b)** reuses #1928's attention-pass computation if it is on `main` by then (REQ-17). Otherwise it reads through `scripts/automation/lib/github.py`, which provides retry, backoff and rate-limit handling, and never through hand-rolled `gh api`. A read failure means no call for that item. The "parked" test is whatever ESC-4 rules, and under (A) it calls the selector's own exclusion predicate rather than a copy.

## 4. Residuals (accepted, disclosed in the S1 PR body)

- **R-1 (security; ARCH-ESC-2): working-tree code holds the credential.** *(Rewritten in round 1, security SF-2: the round-0 text understated it.)* Like every bootstrap script `bin/hos-cron` runs (`get_app_token.sh` reads the App PEM, and `create_branch.sh` and `hos_repo_sync.sh` also run from the tree), the notifier runs, unsandboxed, from whatever the clone's working tree holds. ADR-1605 R-12 already records this for the notifier. Because the notifier now **reads the Pushover credential**, the exposure is:
  - **No merge and no human action is needed.** The sandboxed worker agent can write the clone's working tree, and a worker branch is routinely left checked out between cycles (this clone is on one as this ADR is written). A prompt-injected agent can therefore plant code that the next unsandboxed pre-auth notifier call (`token-mint-failed`, `usage-pause-fail-closed`, `cron-lock-stuck`, or a cross-issue caller) runs with the credential in memory. Round 0's "an unmerged branch must be checked out in a cron clone" described the same thing as if it were a precondition; it is the normal state.
  - **The surface is larger than the two notifier files.** It includes `bootstrap/notify_human.sh`, `bootstrap/lib/notify_human.py`, and everything AD-11 loads into the same process: `scripts/automation/lib/cycle_log.py`, `scripts/oversight/lib/audit_log.py` (which `cycle_log` loads by path) and their imports. AD-11's late import narrows the window but cannot close it (CPython cannot zero a `str`, and on the `timeout` path the stuck HTTP worker still holds the values).
  - **What it buys an attacker:** the Pushover application token and the human's user key. That lets them send pushes to the human (impersonating HOS) and spend the app's quota (which would silence the real channel with 429s). It does **not** add a capability beyond what the same attacker already has through `get_app_token.sh` and the App PEM, which is the higher-value secret in the same class, reached by the same route.
  - **Hardening evaluated and rejected for S1** (security SF-2 (b)):
    - *Self-check of blob hashes against `origin/main` before reading the credential.* Rejected. The check would run inside the very code it is checking, so a modified `notify_human.py` simply omits it. Moving it into `bin/hos-cron` does not help either, because `bin/hos-cron` also runs from the same writable working tree. The `origin/main` ref lives in the same writable `.git`. A check that an attacker who can write the tree can also delete is theatre, and it would add a new fail-closed path (drift → silence) to a channel whose purpose is to never be silent.
    - *Run from a `git archive origin/main` extraction.* Kept as follow-up N-2, not S1. It only helps once the extraction's source is something the sandboxed agent cannot rewrite, which is the same launcher-level question as for `bin/hos-cron` itself.
  - **The real fix is at the launcher, not in this feature:** cron must run `bin/hos-cron` and everything it calls from a checkout the sandboxed agents cannot write. That is recorded as follow-up **N-4** (§10). The S1 PR body must state all of the above at ARCH-ESC-2.
- **R-2 (reliability): at-most-once is not exactly-once, and the push volume is now bounded.** *(Rewritten in round 1, reliability MUST_FIX-2.)* A duplicate push is still possible:
  - after a delivery the server accepted but the notifier timed out on (ambiguous attempt);
  - after a send whose record rewrite failed;
  - when the state is untrusted or unusable.
  
  Separately, a contention loser that times out on the lock and whose final lock-free read finds no fresh record reports `undelivered` to its caller even though the winner may have delivered. Every one of these leans toward too many pushes, not too few. **The ceilings** (computed for the 15-minute cron cadence, 2 roles per project, and the AD-14 one-call-per-cycle cap; Pushover's free per-application limit of 10,000 messages a month is taken from its public documentation and was not verified live):
  - **State usable (`ok` or `fallback`), endpoint healthy:** at most **one push per key per 6 h**, so at most **4 per key per day**.
  - **State usable, endpoint slow-but-accepting (every call times out):** pushes at 0, 30 min, 1.5 h, 3.5 h, 7.5 h, then every 6 h: **7 per key on the first day and 4 per key per day after**. Round 0 had no ceiling here (up to 96 per key per day at high priority).
  - **State usable, endpoint down or rate-limited:** no pushes are delivered, so no volume; the global cool-down limits the network attempts to one per 5 min (one per hour for 429) machine-wide and stops each call paying 25 s.
  - *(Round 2, reliability NOTE-C.)* **State root unusable, or state directory hung, and endpoint down:** there is no cool-down in the `unusable` tier, and a watchdog exit on a hung state directory writes none either, so each #2125-owned call can pay its full 25 s (32 s at the caller's kill). Both outcomes (`network`, `timeout`) take the AD-14 slot, so this costs **at most one such call, 32 s, per role and project per cycle**, plus any cheap calls inside the 10 s budget. It costs time, not pushes.
  - *(Round 2.)* **Unusable tier and trigger fairness.** In the `unusable` tier no outcome is cheap (there is no dedup, so every call sends and takes the slot), so while two #2125-owned conditions persist, the one earlier in code order is pushed every cycle and the later one is logged `alert=skipped:cycle-cap` every cycle. That is accepted: the human is being pushed every 15 minutes in that state, the skipped trigger is visible in the cycle log, and fixing `~/.hos` restores both.
  - **State root unusable (`unusable`):** no per-key ceiling exists, because no state can be kept. With the AD-14 per-cycle cap and the missing-lock-directory rule, the #2125-owned triggers make **at most one push per role and project per cron cycle**: **96 per role-project per day, 192 per project per day**, all at priority 0 (no quiet-hours ringing). A single project would use about 5,800 of the 10,000 monthly quota if the state root stayed unusable for a whole month; two such projects would exhaust it in about 26 days, after which Pushover answers 429 (`rate-limited`) and nothing is delivered until the month resets. That is **accepted and disclosed**: it requires `~/.hos` to stay unusable for weeks while the human is being pushed every 15 minutes about it. The cross-issue callers add to this only on their own cadences (ADR-1605 retries hourly only while `undelivered`, and a stateless send is `sent`; ADR-2100 fires once per filed item).
  - **Per machine, state usable:** the sum over keys. Keys are bounded by the 9-cause table × projects × targets, and in practice by how many distinct problems exist at once.
- **R-3 (product, literal rule): dedup is per (project, cause, target), not per fingerprint.** If an ADR-1605 G-4 re-alert or a fingerprint change keeps the same cause and tracking issue within 6 h, it is deduped. ADR-1605 records it as `sent` (exit 0), and the detail is on the GitHub item. That is the issue's literal "one push per `cause+issue` per 6 h", and AC-40 assigns dedup to #2125. A **different** cause, or a new tracking issue (ADR-2100 files a new item per fingerprint), is a new key.
- **R-4 (operational; ARCH-ESC-1): no proxy support.** A host that can reach `api.pushover.net` only through an HTTP proxy cannot use the channel. `--test` reveals that at setup time, as `reason=network`.
- **R-5 (security, same class as ADR-2100 AD-11): suppression by environment control.** A writer who can set `HOS_STATE_DIR` in an unsandboxed cron process's environment can plant "sent" records and suppress pushes. A forged future `sent_at` or `attempt_at` is refused, and since round 2 so is a `_global.cooldown` whose `until` exceeds its reason's period (AD-8), but fresh, in-bound forgeries can be planted continuously. *(Round 2, security NOTE.)* A writer with group write on `~/.hos` **before** the notifier's first `fchmod` of the state root can plant foreign-owned entries (`notify` as a foreign directory, a foreign `notify-fallback.rec`) and, by re-planting faster than the notifier's single unlink-and-retry (AD-8), push it through the fallback tier into the `unusable` tier. The result is delivery at normal priority (`STATELESS_PRIORITY`, ARCH-ESC-3), not silence. This is the same actor class (control of the state root), so it adds no new capability. The same writer could set the AD-7 overrides; since round 1 that is marked in every audit event (`mode=test-override`) rather than silent. A trust-store substitution through `SSL_CERT_FILE` is **closed** in round 1 (AD-5). AF-5 shows that a branch cannot do this, so the writer must already control the crontab or the caller. AD-4's passwd-home rule removes the equivalent route for the credential.
- **R-6 (privacy, human-ruled channel): a third party holds the message text.** That text is the cause, project, role, the issue URL (which includes the repo slug, even for a private repo), and `--since`. Pushover keeps it under its own retention policy. The human ruled both the channel and the template, which carries the issue URL. AD-9 keeps everything else out.
- **R-7: until S2 and S3 merge, nothing in #2125 calls the notifier except `--test`.** Its value arrives with S2, S3 and the cross-issue callers (ADR-2100 S2, ADR-1605 Part 3, #2123).

That is deliberate, but it must not ship as an architect default: **S1 does not merge until the human's answer to ARCH-ESC-3 is recorded**, both in the S1 PR body and as a dated revision note on this ADR.
