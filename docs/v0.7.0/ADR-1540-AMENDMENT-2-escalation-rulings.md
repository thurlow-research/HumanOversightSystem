### AF-6 (NEW — severity **HIGH** for the human's H1 decision, and it corrects **my own AM-3**): the cutover set is **at least 93 issues**, not "far smaller than 46."

AM-3's heading asserts *"The volume is far smaller than 46."* **That sentence is wrong, and I wrote it.** Measured this session with the exact query AM-3 itself names as the bound:

```
bash bootstrap/query_issues.sh --app worker --list --milestone "v0.7.0 — Quality" --label needs-ai --state open
  → 93 open, non-PR, dispatch-labelled issues in the active milestone
```

**Read this number precisely — it is a floor with two error bars in opposite directions, and both matter:**

- **It is a floor, not an exact count.** `query_issues.sh --list` issues a single `per_page=100` page with no `--paginate` (`bootstrap/query_issues.sh:190`), then filters PR records. 93 non-PR records could be a full 100-record page containing 7 PRs — and PRs in this repo *do* carry `needs-ai` (`worker-cron-prompt.md:75`). The unfiltered milestone query returns exactly **100**, i.e. it is truncated. So ≥93, possibly more.
- **Not every one of the 93 needs a human act.** An issue authored by `ScottThurlow` is trusted by AD-1(a); a bot-authored issue matching a machine-filing marker is trusted by AD-2; and an issue that already carries a `labeled`/`milestoned` event by a human CODEOWNER (#1643 is the live example) is already authorized. The number requiring an act is the untrusted-authored subset that lacks such an event. Using the TD's FIND-3 distribution (46 human-proxy / 32 worker / 15 overseer / 7 human of 100 open issues) as a rough guide, that subset is a substantial majority — but it is **not measured**, and measuring it costs one events call per candidate.

**The architecturally interesting consequence, which is what actually decides AM-14:** the authoritative count *cannot be obtained before S2 merges*. Deriving it requires running the gate's own authorization test against every candidate, and the gate is what S2 ships. TD §2.7.3 already identifies the gate's `ALL-CANDIDATES-GATED` output as "the only listing that cannot drift from the gate, because it *is* the gate" — and that output exists only post-merge. **A pre-merge pass therefore cannot be sized before it is performed.** That is not an inconvenience; it is a reason not to recommend one.

**Where AM-3 was right and where it was wrong.** Right: the cutover set is *defined* by the gate's own query, not by the open backlog, and "46 issues on day one" was the wrong frame. Wrong: I inferred from that boundary that the *volume* was small. Bounding a set by a query says nothing about its cardinality, and I asserted the cardinality without running the query. That is the same defect I flagged in Amendment 1 §3's closing note about the unverified 46/100 counts — a load-bearing number asserted rather than derived — committed in the same document that flagged it. Recorded in §2.

### AF-7 (NEW — severity **LOW** as evidence, **MEDIUM** as a latent method defect): the duplicate-`labeled`-event scan had a real pagination defect, it was fixed and re-run, and on this corpus the defect changed nothing — **78 issues, zero duplicates, zero issues above one event page.**

**What was run, in two passes, and why the second exists.** The dispatching worker first scanned the 52 most recently updated non-PR issues, walking every `labeled`/`unlabeled` event for a second `labeled` on a label already held with no intervening `unlabeled`. Result: zero. I read the script (`/tmp/claude/scan_dup_labels.sh`) rather than taking the summary on trust, and found a real defect: it fetched `issues/<n>/events?per_page=100` with **no pagination** — the same defect as FIND-2, which this design exists in part to fix. GitHub's issue-events endpoint returns oldest-first, so any issue above 100 events would have been read at its *earliest* history and been invisible at its most recent.

**I asserted that this mattered. It was checked, and it does not — on this corpus.** The scan was re-run paginated and wider (`/tmp/claude/scan_dup_labels2.sh`, `--paginate`):

```
--- paginated scan: 78 issues; 0 with a duplicate labeled event ---
--- issues exceeding one event page (invisible to the v1 scan): 0; max events on one issue: 17 ---
```

**No issue in this repo has ever exceeded one page of events; the maximum is 17.** The population I identified as the blind spot is **empty**. The v1 scan was not in fact blind anywhere, its null result is exactly as strong as its raw count suggested, and the result now holds across **78** issues rather than 52.

**I am recording my own error here on the same terms as AF-6**, because the symmetry is the point: AF-6 is a claim of mine that was reasoned rather than measured and came out *worse* when measured; my first reading of AF-7 is a claim of mine that was reasoned rather than measured and came out *better*. **An amendment that overstates the weakness of its own evidence misleads the human at H1 exactly as an overstated strength would**, and it would have sent the panel to re-attack a blind spot that does not exist. The correction cost one command. Both instances belong to the same root cause and are recorded together in §2.

**What survives, and it is the whole of the limitation:** absence of a duplicate event may reflect absence of the **attempt** rather than suppression of the event. Nobody in this repo's history has had a reason to re-apply an already-present label, so a corpus with no attempts and a corpus with suppressed events are indistinguishable. This is unaffected by pagination, by corpus size, or by anything else a read-only scan can do. **It is why §0.6 gap 6 stays open, and my conclusion is unchanged: 78/0 raises confidence in E-5's premise and does not close the gap.**

**The pagination defect is still worth recording as a latent method defect, and that is the MEDIUM.** It had no effect here only because this repo is young and its issues are short. It would bite on an older or busier repo — a consumer deployment, or this repo a year from now — and it would bite *silently*, returning a clean null while reading only ancient history. A scan whose correctness depends on a corpus property nobody checked is one repo-growth away from being wrong, which is the same shape as the `E2BIG` class (#1364) and as FIND-2 itself.

**Both scan scripts are `/tmp/claude/` throwaways and are NOT committed, so neither is reproducible from the repo.** That is a gap, and I am asking for it to be closed: per `CLAUDE.md`'s *"the second time you need it, it belongs in `scripts/` with a test"* — and this is already the second time — **the paginated version should land in `scripts/` as a committed, tested check.** The panel is asked (R1) to re-examine this premise and currently has no way to re-run the evidence it is being handed; a consumer deployment inheriting this gate has less. **Requested as a follow-up issue**, not folded into S2: it is a verification tool, not part of the critical-path fix, and it must not become a sixth thing S2 carries.

**The decisive check for gap 6 — a live mutating re-apply — is unchanged by any of this**, because no read-only scan of any width can distinguish "no attempt" from "event suppressed." See AM-14's closing paragraph for the check, its scope, and my authorization. It is not a precondition for anything I rule here, because AM-15 is written to be *invariant* to the answer.

## 1. Rulings

### AM-14 — E-5, question 1 (does AM-3's cutover recommendation stand?). **NO. My single-pass recommendation is WITHDRAWN.** The default is the lazy drain, with a small **primed head**. AM-3's binding rules are unchanged; only its volume claim and its recommendation fall. (Amends **AM-3**.)

AM-3 said, as a recommendation and not as a binding rule: *"a single pass over the active-milestone dispatch-labelled set immediately before S2 merges, so the first post-merge cycle is not a silent no-work cycle."* Three things have changed since I wrote it, and each alone would be enough:

1. **The volume is ≥93, not "far smaller than 46"** (AF-6). At two acts per issue that is **≥186 GitHub UI acts**, each of which must complete without interruption.
2. **The act is two-step, not one-step** (E-5, which I accept in full). "One click per issue before merge" and "remove-then-re-add on ninety-odd issues" are different propositions, and the human was shown the first.
3. **The pass cannot be sized before it is performed** (AF-6, closing). The number of issues genuinely needing an act is knowable only by running the gate's authorization test per candidate — which is the thing S2 ships. Recommending a pre-merge pass of unknown size, priced at twice the advertised rate, is not a recommendation; it is an open-ended request.

**Binding, replacing AM-3's recommendation:**

> **The default cutover is the lazy drain**, which AM-3 already ruled safe and which nothing here changes: an issue that nobody is about to build costs nothing, and the authorizing act is performed at the moment the human decides the issue is next — an act they already perform implicitly today by deciding it.
>
> **Plus a primed head, bounded by intent rather than by the backlog:** immediately before S2 merges, the human authorizes only the issues they actually want built in the first days after merge — the working expectation is **single digits**, and #1539/#1540 themselves are the obvious first entries. This is not a subset of a pass; it is a different act with a different justification. A pass drains a queue; a primed head keeps the worker fed while the drain happens lazily. It costs the human a handful of acts and it removes the one failure AM-3's pass existed to prevent.
>
> **AM-13 remains the backstop and is unchanged.** The gate's `ALL-CANDIDATES-GATED` line is what makes the lazy drain safe to choose: a fully-gated queue announces itself rather than looking like an empty backlog. AM-13 was pulled forward from S6 for exactly this moment, and with the single pass withdrawn it is load-bearing rather than precautionary. **A reviewer who proposes dropping it is proposing to make the ruling above unsafe.**

**What remains the human's, and it is narrower than before.** AM-3 offered the human a choice between a pass and a lazy drain. With AF-6's number in hand, the pass is no longer a choice I will put in front of them as an equal option — an architect who recommends a ≥186-act manual procedure whose size cannot be determined in advance is asking the human to absorb a design cost. The human retains the right to do a pass anyway, and may of course decide the primed head should be larger. **What they are being asked to clear in ESC-6 item 2 is the standing per-issue obligation at its true price (two acts), not a cutover plan.** §3(b) H1 item 2 is rewritten accordingly.

**On closing §0.6 gap 6 — the decisive check, who runs it, and my authorization.**

The decisive check is a **live mutating re-apply**: from a human account, apply a label an issue already carries, then read that issue's event list (paginated, and from the *newest* end) for a second `labeled` event with no intervening `unlabeled`. Nothing short of a mutation answers it. AF-7's paginated 78/0 scan is already the strongest read-only evidence obtainable on this corpus, and it still cannot distinguish "the event was suppressed" from "nobody ever attempted it" — so no further scanning, of any width, will close this.

**I authorize it, scoped, and the scope is not a formality:**

- **On a throwaway surface only** — a scratch issue created for the purpose, or a scratch label on an already-closed issue. **Never on a live candidate issue.** A stray `unlabeled`/`labeled` pair by a human account on a real issue is, after S2, *indistinguishable from a cutover authorization act* — the probe would write the very signal the gate reads, and would do it before the gate exists to make it legible. Contaminating the evidence base of an authorization mechanism in order to test the authorization mechanism is the kind of self-defeating experiment that is obvious only after it has been run.
- **Run by the `coder`, under a bot identity, as a named S2 acceptance check** — not by the human and not by the worker on live state. The idempotency behaviour under test is a property of the GitHub API, not of the actor, so a bot-actor probe answers the question at strictly lower cost and with no human time. It stays where the TD already put it: §6.2's acceptance list.
- **It is a confirmation, not a precondition.** **No ruling in this document depends on the outcome**, because AM-15 is written to be correct either way. If the check shows a re-apply *does* emit a fresh `labeled` event, E-5 dissolves, the second act becomes unnecessary, and the human's burden halves — AM-14's lazy-drain default is still right, because it was never justified by the two-act cost alone. Report the result on #1539 either way; a gap that has been closed should stop being carried as open.

### AM-15 — E-5, question 2 (should "remove and re-add" be written into the cutover material?). **YES — verbatim, with the reason, and worded so it is correct whichever way §0.6 gap 6 resolves. The milestone route is FORBIDDEN as a cutover route.** (Adds a binding operational clause to AD-4; amends nothing in Amendment 1.)

**On writing it down.** AM-1's demand was absolute and it decides this: *a gate whose documented approval path silently does nothing is worse than no gate.* An instruction that says "apply the `needs-ai` label" to an issue that already carries it is that exact failure — the human performs it, the UI accepts it, nothing happens, and the issue stays gated with no signal that the act failed. Writing the harder-but-true instruction is not optional and the "it looks like churn" objection does not survive contact with it.

**And the churn objection is wrong on its own terms**, which is worth stating because `technical-design` raised it in good faith. An `unlabeled` followed by a `labeled`, both by `ScottThurlow`, is **not** an undo-redo. It is the authorization record. It is the only durable, GitHub-reported, unforgeable evidence that a human CODEOWNER authorized this specific issue at this specific time — which is precisely what AD-4 says authorization *is*. A reader of the event log who sees it as churn has misread the mechanism, and the fix for that is one sentence in `docs/LABELS.md`, not a quieter act.

**Binding — the instruction's required shape.** The cutover material (and anything else that tells the human how to authorize an issue) MUST state the act in a form that is correct under both resolutions of §0.6 gap 6:

> **To authorize an issue, apply the dispatch label to it from your own GitHub account** (web UI, mobile app, or a personal-access-token `gh` invocation under your own login — **never** `edit_issue.sh --app human`, which writes as `scottthurlow-claude[bot]` and does nothing).
> **If the issue already carries the label** — which every issue already in the queue does, and which you will notice because the UI offers you *removal* rather than addition — **remove it first, then re-add it.** The remove-then-re-add is not undoing anything: the pair of events it writes, both under your own account, *is* the authorization record the gate reads.

This wording requires no prior knowledge of GitHub's idempotency behaviour and is correct whether or not a bare re-apply emits an event, because it routes on what the UI actually offers. That is deliberate: an instruction to a human should not depend on a fact the repo has not yet verified (AF-7).

**Binding — the milestone route is forbidden, and this is a mechanical finding rather than a preference.** TD §2.7.4's route table marks the milestone route "riskier" and says "prefer the label route." That understates it, and I verified why:

- `bin/hos-cron:1018-1024` fetches `issues?milestone=none&state=open` every worker cycle, and `worker-cron-prompt.md:33-43` Step 0 triages **every** milestone-less issue — assigning a milestone (step 1) *and* applying `needs-ai` (step 3).
- So the instant the human removes the milestone, the issue becomes eligible for Step 0. The next worker cycle may re-milestone it and re-apply the dispatch label, **both as `hos-worker-hos[bot]`**. The human's remaining additive act on *both* channels is consumed by a bot, and the issue is left un-authorizable through either until the human performs a further remove-then-re-add.
- The label route has no such exposure, and I checked rather than assumed. Two facts together, neither sufficient alone: the issue **keeps its milestone throughout**, so Step 0 — the only path that applies the label unprompted — never sees it; and the only *other* site in the entire repo that adds `needs-ai` is `label-swap.yml:74` (`/approve`), which fires only on a human comment. The window between the human's remove and re-add is therefore uncontested by any automation in this repo **as it stands today** — a qualification that matters, and which §3(c) hands to the panel.

> **Binding:** the cutover and per-issue authorization procedure uses the **dispatch-label route only**. The milestone route MUST be documented as **not a cutover route**, with the Step 0 race as the stated reason. The milestone channel remains a valid *authorization source* in the gate (AD-4, as narrowed by AM-4) — a human placing a **new** issue into the target milestone still authorizes it. What is forbidden is instructing a human to *remove and re-apply* a milestone on an issue already in it.

**Also binding, and it belongs with this ruling:** `/approve` must be documented as **actively harmful to the authorization path in the S2 era**, not merely ineffective. On an issue that does not yet carry the dispatch label, `/approve` applies it as `github-actions[bot]` — consuming the one genuinely additive act the human still had, and converting a one-act issue into a two-act issue. TD §2.7.2's replacement confirmation wording must carry this, not only "this did not authorize anything." AM-17 makes the workflow edit that delivers it a named part of S2.

### AM-16 — E-5, question 3 (is this an argument for pulling AM-6 point 4's comment-reading forward from S3?). **NO. AM-6 point 2 stands: S2 is event-only.** `technical-design` was right not to propose it and right to raise it. (Confirms AM-6 point 2; amends nothing.)

E-5's point 3 is factually correct and I verified it rather than conceding it: `label-swap.yml:29` has no label-state precondition, so a `/approve` comment is a **single** act available on an already-labelled issue. It is the strongest argument for AM-6 point 4 that exists. I have weighed it and I am holding the line, for three reasons in ascending order of weight.

1. **The cost that motivated the question is no longer there.** AM-14 replaces a ≥186-act pre-merge pass with a single-digit primed head and a lazy drain. Two acts at the moment the human decides an issue is next — an act of deciding they already perform — is not a burden that justifies advancing a new authorization channel onto the critical path.
2. **The comment channel is irrevocable by construction, and its bounds are S3's content.** Every event-derived authorization has a natural clearing act: `unlabeled`, `demilestoned` — which is exactly what AM-8's S3 rule formalises. **A comment has no inverse.** There is no "uncomment" event, and a deleted comment leaves no timeline record the gate can read. A `/approve` typed months ago on an issue since rewritten would authorize it indefinitely, and the two mechanisms that bound that — AD-5's digest binding and its ordering invariant (approval newer than assessment) — are *precisely* what S3 introduces. Shipping the channel in S2 and its bounds in S3 means S3 is retrofitting invariants onto live authorization semantics rather than adding a channel already inside them. **The ordering is not an accident of the build plan; the channel and its bounds are one design.**
3. **The decisive one: it puts a newly-specified authorization channel on the critical-path fix, before the panel has examined the channels that already exist.** S2 is the live fix for an open `priority:critical` on a public repo. The comment channel's entire correctness rests on anchoring to the GitHub-reported comment author — and the failure mode of getting that wrong is an issue's own body claiming its approval, which the TD itself names as the attack to watch. That is the **same class of fact as AF-5**: a four-line workflow whose `env:` block silently determined whether a whole authorization path worked, unnoticed through an ADR, a design and five days, found only when someone read it. I will not add a second instance of that class to the commit that closes the first one, with the dual-lens panel still ahead of us. S2's job is to close a hole, not to open a new door in the same change.

> **The "skip a milestone-less record" rule is retained deliberately, as fail-closed on an invariant violation — not as a carry-forward. The question was exactly the right one to ask — the premise that made the rule *safe* under revision 1 was indeed removed by AM-4's inversion, and noticing that a justification has evaporated while its conclusion survives is the discipline that catches real defects. Here the conclusion survives on different and, I think, better grounds:

1. **The invariant is server-side and explicit.** The gate queries `&milestone=<n>` (the same shape as `probe.py:408`, verified). Every record in the response carries a milestone object by construction. A record without one does not mean "this issue has no milestone" — it means **the response is not the shape the design assumes**: a schema change, a proxy, a mock leaking into production, or a different query than the one specified. Under a violated invariant, "evaluate a narrower channel and carry on" is a decision made on a premise known to be false at the moment of making it. Refusing the candidate is the only response that does not.
2. **The cost asymmetry is one-sided, and that is what settles it.** If the invariant holds, the skip branch is unreachable and costs nothing, forever. If it is violated, the skip costs one candidate deferred until a human looks — pure availability, fully recoverable. The alternative costs an authorization decision taken under a demonstrably-wrong model of the data. This ADR has now found three defects of one shape (FIND-1, AF-5, and AD-4's `is_bot_reviewer` rule): **authorization surviving a condition nobody reasoned about.** I am not adding a fourth site where it can happen.
3. **The decisive one, which I do not think the escalation saw: the skip rule and AM-4's derive-the-title-from-the-record construction are two halves of one thing.** Under AM-4 the expected milestone title is taken from `issue["milestone"]["title"]` — the record's own field. That is sound *only* because the server-side filter guarantees the record's milestone **is** the milestone under which the candidate is being selected. When the milestone object is absent, that guarantee is the very thing that has just failed for this record. Falling back to the labeled channel means continuing to trust a query whose contract demonstrably did not hold for the record in hand. Keeping the derive-from-record title while dropping the skip is not a smaller design; it is an **inconsistent** one. `probe.py`'s milestone strategy is in the same position for the same reason, as the TD correctly observed.

**On the widened acceptance criterion — confirmed, and it is the right kind of cost.** AM-4 withdrew "all fifteen tests pass unmodified" for "any existing test that asserts a `milestoned` event authorizes." `technical-design` is right that the real figure is **five**, not one: `tests/automation/test_probe.py`'s `_make_issue()` (`:41-46`) emits no `milestone` object, so all four `TestProbeRepoMilestone` cases have their records dropped before `_verify_codeowner_actor` is reached. **I accept the widening and I do not regard it as a cost worth minimising.** A fixture used by `TestProbeRepoMilestone` that emits no milestone object does not represent any response the milestone strategy can receive; it is a wrong fixture that happened not to matter. Read against the TD's own panel surface **R2** — *"nothing in this repo has ever exercised the field FIND-1 is about"* — fixing those four fixtures is not overhead at all. **It is closing the test-coverage gap that FIND-1 lived in undetected**, and it is the single most useful line item in the S1 test plan.

**One addition, and it is the same principle as AM-5's bound-hit diagnostic, not a redesign:**

> When the skip fires, the gate (and `probe.py`) MUST emit a one-line stderr diagnostic naming the issue number and the reason (milestone-scoped response contained a record with no milestone object). An invariant violation that is silent is an invariant violation nobody will ever learn about, and a branch asserted to be unreachable should be **measurably** unreachable rather than assumed so.

Recording the reasoning in the design is required, not optional: §1.6 row 4, §2.3 D5.2 and F17 must each carry it, in the ruling's own terms, so the next reader inherits the argument rather than the bullet.
