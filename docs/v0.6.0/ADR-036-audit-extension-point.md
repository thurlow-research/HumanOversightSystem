## 1. Context and the disciplined asymmetry

ADR-035 was the high-water mark of making git do WORM-grade, role-enforced audit storage: a deterministic approval bot, an identity-bound gate exception, a fourth approval-bearing identity class, three ADR revisions, and a dual-lens panel. It was still a git/PR mechanism wearing production-audit clothing, and its panel found a HIGH forgery gap that three prior passes — two of them mine — missed. The human's resolution is to stop pretending: **audit recording becomes an extension point.** HOS defines a storage-agnostic contract; a real deployment brings its own backend (WORM, SIEM, append-only RBAC DB); HOS ships a prototype-grade default whose security holes are documented as accepted.

The engineering discipline is **asymmetric rigor**, and I bind it as the organizing principle of this ADR:
- **The contract is where rigor goes** (AD-1 … AD-4). It is the one piece that cannot be cheaply changed — every future backend depends on its shape. The failure mode to prevent is a git characteristic leaking into the interface (FR7). If the normative text says "records are JSONL appended at path X," nothing else can ever implement it.
- **The default backend is explicitly disposable** (AD-5 … AD-12). Its shape is fixed by the human and I do not re-litigate it: local append → sweeper collects into a PR → **overseer approves** → merge to protected `main`, zero bypass actor. I design the requirements *around* it so it is a faithful, minimally-secure reference implementation and so swapping it is genuinely possible.

**I confirm pm-agent's shape ruling and make it concrete: contract-shaped at the interface, adapter/driver-shaped at the implementation, not pack-shaped** (AD-1).

## 2. Decisions

### AD-1 — The extension point: a new `contract/AUDIT-RECORDING-CONTRACT.md`, one pass-on operation behind an adapter selected by config, with a conformance check. (BINDING — architecture; the new contract file is a protected surface held for structural sign-off.)

pm-agent ruled it is not pack-shaped (packs inject prose; this is a runtime functional sink) and positioned it as contract-at-interface + adapter-at-implementation. **I confirm, and I fix the concrete mechanism:**

- **Where the interface lives — a NEW sibling contract document, `contract/AUDIT-RECORDING-CONTRACT.md`, referenced from `contract/OVERSIGHT-CONTRACT.md`, not folded into it.** Rationale: `OVERSIGHT-CONTRACT.md` defines *what a compliant agent TEAM produces* — its consumer is an agent team. The audit-recording contract defines *what a compliant audit BACKEND must implement* — its consumer is a backend author, a different axis entirely. A sibling doc keeps the two conformance surfaces from bleeding together, and `contract/**` is a protected surface, so the interface can never be loosened without a human (correct — it is the one piece that must not drift).
- **One pass-on operation behind a HOS-owned dispatcher (FR1/FR3).** HOS producers call exactly one operation — architecturally `record_event(event) -> Outcome` — implemented once as a HOS-owned dispatcher that forwards to the *configured adapter*. No producer names a storage medium; no producer may write to any store except through this operation. The dispatcher, the record type, and the `Outcome` enum are HOS-owned; the **adapter** behind them is the swappable part.
- **Selection is configuration, not a code edit (FR6).** A new `AUDIT_BACKEND=` key in `config.sh` (exactly the way `PACK=` is recorded) names the active adapter. Default = the prototype adapter (AD-5). Replacing it edits config only; HOS core is untouched. `technical-design` chooses whether adapters are discovered by name from a known directory or registered explicitly, but the selection surface is `config.sh`.
- **Conformance is explicit and checkable (FR6).** A conforming adapter implements the FR3 pass-on operation, accepts the FR2 record shape, declares its FR4 failure semantics, and — because AD-2 rules there is **no** mandatory read capability — needs no query interface. A `verify_audit_backend` conformance harness validates an adapter against the contract; its decisive case is the **write-only stub** (AD-2's acceptance test): a stub that only counts records must leave every HOS producer *and* every operational read working. A non-conforming adapter fails the harness rather than silently mis-storing records.

`technical-design` owns exact file paths, the dispatcher module location, and the adapter interface signature; the architectural rule is **one operation, one dispatcher, config-selected adapters, a conformance harness whose acceptance test is the write-only stub.**

### AD-2 — The tier boundary (Q3, BOUND — this is the load-bearing architectural decision in the whole ADR). Operational control-flow state stays in a HOS-owned local tier that is always present; the swappable backend is write-mostly audit-of-record with NO mandatory query interface.

This is the decision the task correctly identified as the one that, gotten wrong, either forces every backend to implement a query interface or silently breaks the build pipeline when a backend is swapped. I rule it, and I ground the ruling in AF-036-2.

**The test for which tier a record belongs to — bind this exact test:**
> *Does HOS read this record back to make a control-flow decision?*
> **Yes → operational control-flow state.** It stays in the **HOS-owned local tier** (the `audit/log/**` spool today), which is **always present regardless of the configured backend**, and HOS reads it **only** from that local tier. It is **never** delegated to the swappable backend, and no HOS control-flow decision may depend on querying the backend.
> **No → write-only audit-of-record.** It is what the swappable backend receives. The audit-of-record interface stays **write-mostly**; a conforming backend implements no read/query capability.

**Applied to the verified facts (AF-036-2):** `step-head` / `step-head-final` (per-step base/head-SHA resolution consumed by `oversight-evaluator`, `step_range.sh`, `audit_conditional_proceed.sh`) are operational control-flow state → local tier. They are read back; they belong to the tier that is always present. Genuine audit-of-record events (cycle decisions, the overseer's rulings, the sweeper's own actions) are write-only-for-the-record → swappable backend.

**Two consequences `technical-design` MUST encode:**
1. **The local spool is HOS-owned infrastructure, not part of the backend contract.** All producer records land in the local spool first (they already do). Operational reads *always* hit the local spool — for **any** backend, including the default. So even the default (PR→`main`) backend never requires `main` to be queryable for step resolution: the local spool is authoritative for reads. This is the clean invariant.
2. **The sweep to the backend must never be the sole copy of operational state.** The sweeper carries the audit-of-record subset to the backend, but it MUST NOT prune operational control-flow markers from the local tier while any consumer may still read them back. Operational markers MAY be mirrored to the backend as inert audit context, but the backend is never asked to serve them back. `technical-design` chooses the factoring — a distinct local-only operational stream, or a retention rule on the shared spool that outlasts any in-flight step — but the boundary is: **operational reads never leave the local tier.**

**Acceptance test (bind it, it is the whole proof the boundary is right):** with the audit-of-record backend swapped for the write-only counting stub, per-step base/head-SHA resolution and every other operational read still succeed. If they do, the boundary is correct; if any read breaks, an operational record leaked into the swappable tier and must be moved back.

I reject the alternative (option (b): mandate a read/query capability on every backend). It would make a WORM/SIEM/CloudTrail-style backend implement query-back for HOS's build-pipeline convenience — exactly the storage-assumption leak (FR7) this pivot exists to prevent, and the most expensive kind to unwind. **pm-agent's recommendation on Q3 is correct; I bind it and add the retention/no-prune consequence and the write-only-stub acceptance test, which pm-agent stated as a verify line but did not bind as the deciding proof.**

### AD-3 — The storage-agnostic record contract: mandatory fields, one operation, no leaked storage assumption. (BINDING — FR2/FR3/FR7.)

The contract (AD-1's document) defines the record as **data**, with no serialization or path in the normative definition:
- **Mandatory:** a stable **event type**; a **UTC timestamp** (unambiguous instant); an **actor identity** (which agent/identity the record is *about* — the deciding overseer, the worker, etc. — attribution that survives regardless of who transports the record); and a **correlation key** sufficient to tie the record to the work it describes (build step / cycle / the commit or PR the decision concerns).
- **Optional:** an event-keyed free-form payload; a **prior-record linkage** field a backend MAY use to chain records — the contract *permits* chaining but does not *require* it, so a non-chaining backend still conforms.
- **Excluded from identity:** no mandatory field may be a storage location. "File path," "line number," "branch name," "PR number" may appear only inside the optional payload as data, never as the record's identity.
- **No leak (FR7):** the normative (MUST/SHALL) text of the record schema, the pass-on operation, and the failure/read semantics MUST NOT reference git, pull requests, branches, JSONL, a directory, or any characteristic unique to the default. Any capability HOS depends on is re-expressed abstractly and is satisfiable by a non-git backend — demonstrated by the write-only stub (AD-1/AD-2).

**Acceptance:** the record definition instantiates and validates with no filesystem, git, or network present; a record missing a mandatory field is rejected by the contract's own well-formedness rule; a review of the contract text finds no git/PR/JSONL/path term in any normative clause.

### AD-4 — Failure semantics are part of the contract; "proceed silently unrecorded" is forbidden. The default's pick is the human's (Q2). (BINDING on the contract requirement; the default's choice HELD.)

The contract MUST be able to express three outcomes when recording cannot complete: **block**, **buffer-with-bound-and-retry**, and **explicit-proceed-with-a-visible-marker**. It MUST forbid *silent* proceed-unrecorded, and every outcome MUST be observable to the caller. A production backend MUST be able to declare **block** (a real audit system typically cannot proceed unrecorded); the contract MUST NOT hard-wire "proceed unrecorded."

**This closes a real current defect, verified:** `release_artifact_logic.py` writes its audit event best-effort and `warn`s but never fails on audit I/O ("never fail the release gate on audit I/O"), and no aggregate log reaches `main` today (035 VF-3) — so HOS's *de facto* failure semantic is "proceed, unrecorded, quietly." That is prototype-tolerable but is exactly what a real audit system must never do, which is why failure semantics move into the contract.

**Q2 — the DEFAULT's failure semantic — is the human's**, and I agree with pm-agent that it genuinely is (it changes when and whether the autonomous loop halts on an audit hiccup — user-observable timing + an operational obligation, squarely the product-boundary checkpoint). *My recommendation, not binding:* **buffer-locally-with-a-bound and escalate on stuck** (records accumulate locally, the sweeper carries them, a stuck backlog escalates per AD-10) — never silent, never a hard cycle-halt for the prototype. See Q2 in §3.

### AD-5 — The default backend: local append → sweeper collects into a PR → overseer approves → merge, zero bypass actor. The three required checks pass natively. (BINDING — FR8/FR9/FR10; the human's fixed mechanism, not re-litigated.)

The default adapter (AD-1) MUST: (i) have local producers append to the spool (they already do); (ii) have an **audit-sync sweeper** collect the accumulated audit-of-record into a PR against protected `main`; (iii) have the **overseer approve** that PR; (iv) merge via an ordinary PR merge that satisfies every branch-protection rule and required status check, with **no ruleset bypass actor and no direct push** anywhere (honoring #873). It MUST ship documented — at the point a deployer configures it — as **prototype-grade and expected to be swapped**, with its accepted limitations enumerated (AD-8).

**Native gate satisfaction (AF-036-1, verified — this deletes ADR-035's entire structural centrepiece):** because the overseer *approves* rather than *authors*, `require-overseer-approval` passes on the overseer's approval, `require-human-approval` is N/A (`audit/**` not protected), and `require-tier-ceiling` computes LOW ≤ the default HIGH ceiling. **No exception is carved into any of the three gates.** ADR-035's `require_overseer_approval.py` exception (its AD-3 / Component C), its fourth *approval-bearing* identity class (Component M), and its "overseer authors the PR" premise are **DELETED, not revised.** The audit-to-`main` runtime path needs **zero** gate exceptions.

### AD-6 — The deterministic predicate moves from *approver* to a *required status check* that also verifies author identity. (BINDING — FR11/FR12/FR13/FR14; the workflow + predicate are protected surfaces, held for structural sign-off.)

ADR-035 made the predicate a deterministic *approver* because LLM reviewers are manipulable (`research/findings/adversarial-framing-attack-on-reviewer-agents.md`). Under this design the **overseer is the approver** (an LLM), so that mechanical guarantee MUST NOT be lost — it moves into CI as a **required status check**, not an approver.

- **Where it lives.** A pure, data-in/data-out predicate module under `scripts/framework/**` (protected → trusted-base, human-gated), invoked by a **new required-status-check workflow** under `.github/workflows/**` (protected). The workflow MUST follow the AF-036-4 trusted-base/data-only model: `pull_request_target` (+ `pull_request_review` if it must re-fire on review), checkout pinned to `ref: base.sha`, the PR's audit content fetched as **DATA** at the head SHA and parsed, **never** checked out and executed. A design that shells out to the PR's own checkout reopens #972.
- **What it verifies.** The predicate confirms the audit PR is: (a) well-formed-audit-only against the extension-restricted allowlist; (b) **additions-only**, first-creation-aware (whole-file creation of an as-yet-untracked audit file qualifies; any **modification or deletion** of an existing audit record disqualifies); (c) targets the **protected branch**; and (d) is **authored by the designated producer identity** (FR12 — see AD-9). A PR the overseer approves that fails this check **MUST NOT be mergeable**; a well-formed audit-only PR authored by a non-producer identity **MUST fail** even with the overseer's approval.
- **FR12 is a required control, not an accepted limitation.** Under a diff-shape-only design, *anyone who can open a PR* could craft a well-formed audit append and forge the record of what the overseer decided — the HIGH gap that survived ADR-035's entire dual-lens panel. Binding qualification to the producer identity closes it. This is cheap; it is **not** filed as accepted (AD-8).
- **Carry the six panel hardening rules (FR13), each of which only *narrows* qualification:** (a) target branch MUST be the protected branch; (b) patch-truncation fails closed (reconcile parsed added-line count against the `additions` count; mismatch → reject); (c) the audit glob is **extension-restricted** to inert record formats (`*.json`/`*.jsonl`), so a `.py`/`.sh`/dotfile whose bytes parse as JSON cannot qualify — this also protects AF-036-1's native tier pass; (d) zero-content changes (file-mode, symlink, file-type) are rejected; (e) the diff parser is robust — a content line beginning with `+++` is validated as added content, never misparsed as a header; (f) a periodic scheduled sweep is mandatory (an event-only trigger cannot satisfy stuck-PR escalation — AD-10).
- **Fail-closed and anti-tamper (FR14).** Anything the predicate cannot decisively classify does **not** qualify. No configuration knob may *widen* what qualifies — mirror the `min(trusted_baseline, clamp(env,0,1))` idiom (`run_second_review.sh`); knobs may only narrow.

**Ruleset wiring, stated so it is not missed:** making this predicate a *required status check* is a change to the `main` **ruleset** (a server-side GitHub-admin action) in addition to the new workflow file. The ruleset change is a human/admin action; the workflow file is a protected-surface code change (AD-7). Neither is a runtime bypass.

I re-checked this against `protected_surfaces.txt` (AF-036-3) because a new required status check touches `.github/workflows/**`:

### AD-9 — The producer identity (Q4). Architectural constraints BOUND; the identity SELECTION routed to the human — and I differ from pm-agent's recommendation. (BINDING constraints; identity choice HELD.)

pm-agent recommends running the sweeper under the **worker** identity so "no new identity class is introduced." The task correctly flags this is in tension with the human's earlier reasoning — *the audited party should not have custody of the audit record* — which is what moved authorship away from the worker before. I reconcile it explicitly, because it matters, and I **do not simply adopt pm-agent's recommendation.**

**The reconciliation.** The producer is a **deterministic transport** either way — it sweeps records the harness already wrote to the local spool and opens a PR; it does not free-write record content. So the content-forgery threat is not "the LLM types a fake record"; it is "an actor opens a well-formed audit PR that qualifies." AD-6/FR12 binds qualification to the *producer identity*. **That binding is only as strong as the narrowness of the identity it points at:**
- If the bound producer is the **worker**, the binding is *weak*: the worker is the broadest PR-opener in the system **and** the audited party. Binding "author == producer" to the worker means the one identity that can forge an audit record is precisely the party whose work the audit exists to hold accountable — reintroducing the custody concern a prior human decision closed, and giving the adversarial-framing threat (the exact threat that motivated moving the predicate to a deterministic check) a path to the audit trail.
- If the bound producer is a **narrow, single-purpose, non-approving transport identity**, the binding is *strong*: compromise or manipulation of it yields only audit-append capability over inert data (the low-blast-radius argument ADR-035 §1 already established), and separation-of-duties is preserved — the transport is neither the audited party (worker) nor the auditor (overseer).

**Therefore, BOUND constraints (mine, architecture):**
1. The producer identity that AD-6/FR12 binds against MUST be a **narrow, single-purpose, non-approving** identity. It opens audit PRs and appends inert data; nothing else.
2. The producer MUST NOT be the overseer approver — the open/approve split MUST hold (no self-approval; honoring #873's actor separation and the overseer charter `overseer.md:7` "never opens branches or PRs").
3. The producer MUST hold **no ruleset bypass and no content-write beyond opening PRs** (carry ADR-035 AD-1's invariant).

**RECOMMENDATION (mine, differing from pm-agent):** re-scope the existing `hos-auditsync-hos` App as a **non-approving producer/transport identity** — *not* the discarded approval-bearing fourth class. ADR-035's objection to that identity was that it was *approval-bearing*; a transport-only role is a much lighter reconciliation (a producer entry in `docs/AGENT-IDENTITY.md`, not the discarded Component M). This preserves the human's separation-of-duties reasoning and makes FR12's binding strong. **Where pm-agent erred:** it treated worker-as-producer as cost-free ("no new identity"), optimizing for a metric that does not capture the actual cost — worker-as-producer weakens the very FR12 control the requirements set out to add, and silently undoes a prior human separation decision.

**Routing.** The identity *selection* touches the identity model (`docs/AGENT-IDENTITY.md`, a protected governance surface) and separation-of-duties (a trust boundary), so per the product-boundary checkpoint the **selection is the human's** (Q4). I bind the constraints; the human picks the identity. If the human picks worker-as-producer anyway, AD-8's addendum applies (documented accepted limitation, not a silent default).

### AD-13 — The overseer audit-PR recognition path (Component M) is a REQUIRED component; it keys on the deterministic audit-shape required status check, not on any author-supplied marker; and `overseer.md:7`'s charter MUST be narrowly amended. (BINDING — architecture; the `overseer.md` edit is a protected surface added to the structural sign-off, and its user-observable-behavior/trust-boundary consequence is noted to `pm-agent`.)

**6.1 The finding holds; the mechanism as specified does not run unattended.** AF-036-1 correctly established that the three *server-side required status checks* pass natively for an audit-only diff — but those checks only gate the **merge**; they do not cause the overseer to **submit the approving review**. That decision is made by the overseer *agent* (`overseer.md`, run by `bin/hos-cron --role overseer`), and its review flow fail-closes an audit PR at **three** independent points (TD-VF-036-1, re-verified against the cited lines): step 3b (no `signoffs/validators/step{N}/summary.json` → `HUMAN_REQUIRED`), step 4a (no `.claudetmp/signoffs/step{N}-register.md` → register-completeness bounce), and the charter `:7` scope ("only evaluates and acts on artifacts **the worker produced**"). AD-5 asserted "the overseer approves that PR" as if that capability existed; it does not. The finding is correct and HIGH: without a fix, every audit PR routes to a human every cycle, defeating the unattended audit-to-`main` goal that is the entire point of the default backend. **Component M is confirmed required** — a slice that ships the predicate/workflow/producer without it is inert and MUST NOT be accepted (the AD-12 half-mechanism rule applies to the overseer half too).

**Component M's shape (I confirm TD's proposal, with the fail-closed ordering bound):** add an explicit audit-PR branch to the overseer's review flow, evaluated **before** the worker-build artifact matrix (3b/4a/4b). It takes the audit path **only when the audit-shape required status check (Component I) is decisively green**; on that path it skips the worker-build artifact matrix (an audit PR legitimately has none of those artifacts), still honors `OVERSEER_CEILING` (LOW ≤ HIGH → approvable; a `SAFE` ceiling correctly fails it closed to a human — the AF-036-1 caveat) and the protected-surface rule (`audit/**` not protected → approvable), and approves. **Fail-closed ordering (bind it):** if the audit-shape check is anything other than decisively green — pending, absent, errored, or red — the overseer MUST NOT take the audit path and MUST NOT approve on it; it falls through to normal handling (for a genuine-but-not-yet-green audit PR that means wait/`HUMAN_REQUIRED`, never approve). The open/approve split holds — auditsync **opens**, overseer **approves**, distinct identities — so `overseer.md:53` ("never approve a PR you authored or the worker authored under the same credentials") is not engaged (AD-9 constraint 2).

**6.2 The anti-forgery crux — BOUND. The signal is the deterministic required status check, never an author-supplied marker.** This is the load-bearing property and I bind it explicitly so no downstream reader collapses it:

- **The unforgeable signal is the audit-shape required status check (Component I / predicate G, rule 9).** It runs deterministically on the **trusted base** (AF-036-4 model) and returns green only if the diff is audit-only, additions-only, passes the six hardening rules, **and `author == producer_login` (rule 9)**. Author identity is verified there, in CI, against `machine-accounts.env`'s `BOT_AUDITSYNC_USERNAME` — not by the overseer agent reading PR metadata.
- **Any author-supplied marker — a label, PR title, or branch name — is advisory only and MUST NOT be the gate.** These are author-controlled and therefore gameable: a malicious PR could set any of them to claim audit status. The overseer MAY read them as a convenience hint for *routing* to the audit branch, but the **decision to skip the worker matrix and approve MUST be conditioned on the required status check being green**, never on the marker. TD's Component M lists "author == `BOT_AUDITSYNC_USERNAME`" as a condition; that read is acceptable as **defense-in-depth**, but I bind that it is **not** the security boundary — the required status check is. If the two ever disagreed (a PR whose metadata says auditsync but whose check is red, or vice versa), the **required status check governs** and the overseer fails closed.
- **Why this is sound even though the overseer is a manipulable LLM.** The overseer's approval on the audit path is not a trust-bearing content judgment; it is the mechanical "an `APPROVED` review by the overseer login exists" that `require_overseer_approval.py` needs. Merge additionally requires the audit-shape check green (Component J makes it a *required* check). So the two failure directions are both bounded: (i) if the overseer is manipulated into **approving a forged/non-audit PR**, rule 9's check is red for that PR → it **cannot merge**; (ii) if the overseer is manipulated into **not approving a legitimate audit PR**, the PR simply does not merge → it is a stuck open audit PR → caught by Component K's mandatory sweep and escalated (AD-10). Neither direction lets a forged record onto `main` unattended, and neither drops a legitimate record silently. This is exactly why L1 (the overseer self-attests) is an *accepted limitation* and not a *closed control*: the deterministic check bounds shape and origin; it does not bound truthfulness of content, and the overseer's attestation of content-truth is the residual, prototype-accepted gap.

**Anti-forgery property, stated as a binding invariant:** *no PR can reach `main` through the audit path unless the deterministic audit-shape required status check is green, which requires the PR to be authored by the auditsync producer identity. The overseer's approval is necessary but not sufficient, and its content-judgment is never the anti-forgery boundary.*

**6.3 The charter `:7` MUST be amended — the 035 narrow-reading escape hatch is closed here by Q4.** The task correctly asks whether an equivalent-to-035 narrow reading avoids a charter change. It does not, and I say so plainly:

- **What 035 did:** the analogous collision there was `:7`'s *first* clause ("never opens branches or PRs") against FR2's "overseer authors the audit PR." 035 (AD-16) resolved it **without** a charter change by moving *authorship* to the worker, so "never opens PRs" stayed literally true.
- **Why that hatch is closed here:** Q4 is now human-bound to make the producer `hos-auditsync-hos` **specifically so the audited party (worker) and the auditor (overseer) both stay out of custody of the record** (AD-9's separation-of-duties reasoning, which the human adopted). So the audit PR is deliberately neither worker- nor overseer-produced. The collision here is with `:7`'s *second* clause ("only evaluates and acts on artifacts **the worker produced**") — and the only actor-swap that would satisfy it (make the worker the producer) is exactly what Q4 forbids. There is no narrow reading; the second clause is factually contradicted by the design the human chose.
- **The amendment, narrowly.** Broaden `:7`'s second clause to admit the audit-PR class: the overseer "evaluates and acts on artifacts the worker produced, **and approves audit PRs produced by the `hos-auditsync-hos` transport identity when the deterministic audit-shape required status check is green**." The **first** clause ("never opens branches or PRs") is untouched and remains load-bearing — the overseer still never authors. This is the minimum change that admits the mechanism; it does not grant the overseer any new authoring or bypass capability.
- **Routing.** `.claude/agents/overseer.md` is a `.claude/agents/**` protected surface (I do not edit agent definitions; the coder does, human-gated at build). Amending the charter changes **user-observable actor/merge behavior** (a new PR class now auto-approves and merges without a human in the routine loop) and a **trust boundary** (who the overseer will act on). Per the CORE product-boundary checkpoint this is not a pure-architecture call I can unilaterally land: the charter amendment (Component M) **joins the structural sign-off** to the human, and its product consequence is **noted to `pm-agent`**. It binds only after that clearance.
