**My additional findings:**

- **AF-1 (severity: HIGH — strengthens the security model, constrains where the predicate runs).** `require-overseer-approval.yml` runs under `pull_request_target` **and** `pull_request_review`, with the checkout **pinned to `ref: github.event.pull_request.base.sha`** — the TRUSTED BASE — explicitly to defeat the #972 self-bypass (a `pull_request_review` run defaults to the PR *merge* ref and a bare checkout would execute the PR's own copy of the gate script). **Consequence for this design:** the FR5 shared predicate, when called by the CI gate, loads from the *base* branch and is trusted; the PR's audit content must be fetched as **DATA via the `gh` API at the head SHA and parsed, never checked out and executed** — exactly the model `require_tier_ceiling.py:_fetch_head_python` already uses (writes head content to a temp dir, parses, never runs). This is safe for a hostile PR precisely because audit entries are inert data. `technical-design` MUST fit the predicate's CI call site into this trusted-base/data-only model; a design that shells out to the PR's own checkout reopens #972.

- **AF-2 (severity: MEDIUM — first-introduction is a real edge, not a footnote).** Because the two aggregate logs are untracked today (VF-3), the **first** qualifying audit PR *creates* them. "Additions-only" (FR7) must treat whole-file creation as all-additions (qualifies), while any diff that *modifies or deletes an existing tracked audit line* disqualifies. A predicate that keys "additions-only" on "the file already exists and only grew" would wrongly reject the very first PR. AD-6 binds the file-creation case explicitly.

- **AF-3 (severity: MEDIUM — FR12 is already 80% satisfied; close the last 20% by data, not code).** `machine-accounts.env:37` sets `BOT_ACCOUNTS="${BOT_WORKER_USERNAME} ${BOT_OVERSEER_USERNAME} ${BOT_HUMAN_USERNAME} ${COPILOT_BOT_LOGIN}"` — the audit-approval identity is **not** listed. It does not need to be for FR12 to hold *today*: `require_human_approval.py:is_bot_reviewer` is a **layered denylist** — layer 1 (`user.type == "Bot"`) and layer 2 (`login.endswith("[bot]")`) both catch any GitHub App reviewer regardless of enumeration, so `hos-auditsync-hos[bot]`'s review can never satisfy the human gate. But the enumeration is the belt to those suspenders and the only layer that would survive a future identity that is a PAT machine-user. AD-4 binds adding the audit-bot login to `BOT_ACCOUNTS` as defense-in-depth — a data change, not a code change.

## 1. Context

The #873 ruling is absolute — *"Nobody does direct to main. Ever."* The human confirmed one carve-out: audit-log **records** (what the overseer decided) are not **changes**, and gating the record of a decision on review *before the record exists* is incoherent. The tension: the record must reach `main` (a) through a real checked PR with **no** bypass actor, yet (b) without a human in the routine loop and without the overseer approving its own PR (GitHub rejects self-approval, and `require_overseer_approval.py` demands an approval from the overseer login specifically — which the author cannot supply).

The resolution is a **separate, dedicated, deterministic identity** — the *audit-approval bot* — that approves the overseer's audit PR. Approver ≠ author, so no self-approval conflict. The approver is deterministic Python reviewed by a human, so its trust comes from code review of a small tested function; it is structurally immune to the adversarial-framing-attack class the repo documents against LLM reviewers (`research/findings/adversarial-framing-attack-on-reviewer-agents.md`). **This is not a general "deterministic bots may approve PRs" precedent** (§4 non-goal): it is defensible *only* because audit-log entries are inert data — nothing imported, nothing that changes agent behavior — so a malformed or malicious audit entry has categorically lower blast radius than any code change. Every decision below is scoped to preserve that boundary.

## 2. Decisions

### AD-1 — Reuse `hos-auditsync-hos` under a **narrowed, review-submission-only** scope; no push, no bypass. (BINDING; the scope reduction is part of the FR17 structural change held for human sign-off.)

Reuse the existing `hos-auditsync-hos` GitHub App as the audit-approval identity, per the human's direction (*"it would be a maintainer, but is trusted to stay in its lane… Python so it is testable"*). Do **not** create a new App.

**Rationale.** The identity already exists and follows the `hos-*-hos` per-consumer convention. The objection to reuse would be "its old design gave it write+bypass" — but that design was **never built** (VF-3: no workflow, no bypass configured on the live ruleset per the task brief). So reuse here is not inheriting a dangerous grant; it is **defining this identity's scope for the first time**, downward from what the 2026-06-23 doc *specified but never applied*. A new App would leave `hos-auditsync-hos` as a documented-but-purposeless identity inviting exactly the bypass onboarding VF-2 flags.

**Permission scope — the reduction is the security decision, and it is a strict subset of what any push-based design needs:**

| GitHub App permission | Grant | Why |
|---|---|---|
| Pull requests | **Read & write** | `POST …/pulls/{n}/reviews` (submit the APPROVED / withhold review) requires PR write. This is the *only* write scope. |
| Contents | **Read** | Read the PR diff and head content to run the predicate. **NOT** write — the identity never commits, never pushes. |
| Metadata | Read | Mandatory baseline. |
| Everything else | **No access** | — |
| Ruleset bypass | **NONE** | Ruled out below. |

**Ruled out — permanently, and `technical-design` must not design any of these:**
- **`Contents: read & write`** (the 2026-06-23 grant) — this identity never writes to the repo. Approving a review needs zero content-write.
- **Any ruleset bypass actor / "Always" bypass mode** — this is the exact thing #873 forbids and FR1/FR17 remove. No option, including armed auto-merge (ESC-3), may reintroduce it.
- **Admin / "merge without waiting for requirements"** — reserved to the human admin; not this identity.
- **Any code-review, worker, overseer, or human role** — FR3 disjointness. The identity is exactly one thing: an approver of audit-only PRs.

**Invariant `technical-design` must encode:** there is **no code path** by which this identity acquires content-write or bypass. Its runtime (the deterministic approver) calls only the reviews API. If a future change needs it to push, that is a new work item with its own human gate — not a widening here.

### AD-2 — One shared, tested predicate module is the single authority for "audit-only-and-well-formed." (BINDING — this is the #1135 defence.)

The qualification decision (FR5–FR9) lives in **one** Python module under `scripts/framework/` (protected surface — so it is trusted-base and human-gated), exposing a **pure, data-in/data-out** function — architecturally `classify_audit_diff(changed_paths, added_lines_by_path, existing_content_probe) → AuditVerdict{qualifies: bool, reason: str}`. No network, no `gh`, no model, no filesystem writes inside the function — callers fetch the diff data and pass it in.

**Two — and only two — call sites import this one module:**
1. **The audit-approval bot's approve/withhold decision** (AD-7 disposition). It fetches the PR diff via its own runtime and calls `classify_audit_diff`.
2. **The `require_overseer_approval.py` FR10 exception** (AD-3). Under `pull_request_target`/`pull_request_review` it loads the module trusted-base and fetches the PR head content **as DATA** at the head SHA (AF-1), then calls the *same* function.

**Rationale — this is the whole point.** Two independent implementations reproduce #1135's duplicate-tier-gate defect, and here the drift is worse than a redundant check: the bot could approve a diff the CI gate then rejects (PR stuck forever, FR16), or — the fail-open — the CI gate accepts a diff the bot never actually vetted. FR5's equivalence test is therefore a **binding deliverable**: one fixture suite runs *both* call sites against the same inputs and asserts identical verdicts. `technical-design` specifies exact module path and both import lines; the architectural rule is **one function, two importers, zero copies**.

**Anti-tamper (FR18).** Any configuration knob may only **narrow** what qualifies, never widen it — mirror `run_second_review.sh:60-80`'s `min(trusted_baseline, clamp(env,0,1))` idiom (written for HOS#985, an author self-skipping review). No env var, label, branch name, or PR body may turn a non-qualifying diff into a qualifying one or disable the overseer gate.

### AD-3 — The `require_overseer_approval.py` exception is positively identity-bound: qualify **AND** approved-by-the-named-audit-bot. (BINDING — structural; held for human sign-off per FR11.)

`overseer_has_approved(...)` stays as-is. A new, additive branch treats the overseer requirement as satisfied for a PR **only when BOTH** hold:

- **(a)** `classify_audit_diff(...)` (AD-2) returns `qualifies == True` for the PR's actual diff (re-derived from changed paths + added content, never from label/title/body/branch — FR6); **AND**
- **(b)** an `APPROVED` review exists whose author login case-insensitively equals the audit-approval identity's login, read trusted-base from a new `machine-accounts.env` key (e.g. `BOT_AUDITSYNC_USERNAME`), exactly as `BOT_OVERSEER_USERNAME` is read today.

If **either** condition is absent, the gate FALLS THROUGH to the existing requirement — the overseer must have approved — and otherwise FAILS. **This is the load-bearing line and it must never be a diff-shape-only waiver (VF-7):** "audit-only diffs skip overseer approval" would let *any* audit-only PR merge with zero review from anyone. The identity binding (b) is what closes that hole.

**Fail-closed (FR18).** If the predicate cannot classify the diff — unreadable, ambiguous, unexpected content, head-content fetch failure — it returns `qualifies == False`, condition (a) fails, and the normal overseer requirement applies (the PR then correctly cannot merge without a real overseer approval, and escalates). The gate must **never** treat an unclassifiable diff as qualifying. This mirrors `require_tier_ceiling.py`'s existing "could not score → fail closed (never guess)" posture.

**Stale-review interaction (note for `technical-design`, not a new rule).** If `dismiss_stale_reviews` is enabled, a new commit dismisses the audit-bot's APPROVED review; condition (b) then goes false and the PR correctly re-blocks until re-approved. That is the safe direction — do not engineer around it.

**Ordering with the sibling gates (verified):** for an overseer-authored audit PR, `require_tier_ceiling` passes trivially (VF-1: overseer never approved) and `require_human_approval` passes (`audit/**` is not a protected surface — verified against `protected_surfaces.txt`). So the *only* gate that blocks the audit PR today is `require_overseer_approval`, and AD-3's branch is the *sole* change needed to the CI gate set. No other gate is touched.

### AD-4 — No new hole in the human / protected-surface gates. (BINDING — FR11, FR12.)

- **The audit-bot review never counts as a human approval.** `require_human_approval.py:is_bot_reviewer` already denies it via `user.type=="Bot"` and the `[bot]` suffix (AF-3). Bind **additionally**: add the audit-approval login to `BOT_ACCOUNTS` in `machine-accounts.env` — defense-in-depth for the layer that would survive a PAT-machine-user identity. Data change; carried in the same human-gated PR.
- **The exception never covers a protected-surface or non-audit change — two independent barriers.** (1) The shared predicate is allowlist-and-additions-only (AD-5/AD-6): any diff touching a non-allowlisted path — including any `scripts/framework/**` or other protected surface — fails to qualify, so condition (a) of AD-3 is false. (2) Even in the impossible case that a diff both qualified *and* touched a protected surface, `require_human_approval.py` is an **independent** gate keyed on the path list and would fail the PR regardless of the overseer-gate exception. The audit exception is scoped strictly to `require_overseer_approval`; it does not and cannot loosen `require_human_approval` or `require_tier_ceiling`.

### AD-5 — The audit surface is an explicit allowlist, reconciled to a single source with `overseer.md`'s exempt list. (BINDING on structure; exact membership is ESC-2, the human's.)

The predicate qualifies a path only if it is on an **explicit, human-reviewable allowlist** — never "anything under `audit/`." The allowlist and `overseer.md:208-209`'s exempt-files list are the *same concept* (VF-5) and MUST NOT drift into two definitions: `technical-design` makes the allowlist the single source and either derives the overseer exempt-list from it or references it, so a future edit to one cannot silently diverge from the other. Editing the allowlist is itself a `scripts/framework/**` change → protected surface → human-gated (a new path never rides the exception until a human adds it).

**Recommended default (mine, non-binding — the human owns membership via ESC-2):** `audit/oversight-log.jsonl`, `audit/overnight-loop-log.md`, `audit/log/**`, and `audit/automation/**`. I flag one membership question with real consequence to the human rather than pick it: `audit/automation/**` is where REQUIREMENTS-034's ledgers live, and folding it into *this* bot's exception couples two mechanisms — the human should decide whether 034's ledgers ride this path or are handled separately (ESC-2).

### AD-6 — Additions-only, well-formed, first-creation-aware; fail-closed on anything else. (BINDING — FR7, FR8, FR18, AF-2.)

The predicate qualifies a diff only if **every** hunk is one of: (i) creation of an allowlisted file that does not yet exist on `main` (first-introduction — AF-2), or (ii) an append/addition to an existing allowlisted file. **Any modification or deletion of an existing audit line disqualifies** — this is the primary blast-radius bound (FR7: rewriting the record of what overseer decided is categorically worse than appending a junk line). Every **added** entry must be structurally valid for its format (each added JSONL line parses as one JSON object; markdown-log appends match the expected record shape) — malformed content disqualifies (FR8). Anything the predicate cannot decisively classify → **not** qualifying (FR18). No knob may widen this (AD-2 anti-tamper). The design MUST NOT assume the old gitignore/`audit-log`-branch scaffolding exists (VF-4) — it does not.

### AD-7 — Disposition: withhold-and-escalate, never approve/force/close/rewrite; stuck PRs escalate; the approver is self-auditable. (BINDING — FR13, FR16, FR19; merge actor and cadence are the human's, ESC-1/ESC-3.)

- **Non-qualifying → withhold + escalate.** If a PR presented as an audit PR does not qualify, the bot withholds approval, routes to the repo's standard human-escalation channel, leaves the PR open. It MUST NOT approve, force/bypass merge, close the PR, or rewrite content into a qualifying form (FR13). *Whether it additionally submits a `REQUEST_CHANGES` review vs. silently not approving is ESC-4 — the human's.*
- **Stuck audit PRs escalate, visibly.** A required check erroring, checks staying non-green, or a merge conflict must escalate to a human after a bound; the backlog of unrecorded audit history must be observable, not silent (FR16). *The exact bound rides the cadence/lag decision, ESC-1.*
- **The approver's own actions are auditable (FR19).** Each decision (qualify-and-approve, or withhold-and-escalate, with the reason) is recorded durably as inspectable metadata. To avoid unbounded regress, this record rides along on the same audit path as metadata rather than requiring its own separate mechanism to reach `main`.
- **Routine merge is unattended and bypass-free (FR14):** on qualification + audit-bot approval + green required checks, the audit PR merges with no human action via an **ordinary PR merge**. *Which identity performs the merge, and whether GitHub native auto-merge is armed, is ESC-3 — but no option may reintroduce a bypass actor (AD-1, FR1). I bind that constraint; I do not bind the actor.*

### AD-8 — FR17: supersede and remove the 2026-06-23 bypass design; reconcile the auditsync authority downward. (BINDING on the *what*; the doc edits are part of the structural change held for human sign-off.)

### AD-12 — ESC-A (TD-VF-2): `pre_pr_stale_check.py` #880 reconciles to the single allowlist source; the fourth copy is deleted; a fully-audit-only branch is exempt. (BINDING — mine.)

TD-VF-2 is correct and it is blocking: `pre_pr_stale_check.check_audit_log_not_committed` (#880) returns a violation whenever `audit/oversight-log.jsonl` or `audit/overnight-loop-log.md` appears in the diff of any non-`main` branch, and its `_AUDIT_ONLY_FILES` frozenset is a **fourth** hardcoded copy of the audit-file set (alongside `overseer.md:208-209`, the AD-5 allowlist, and the predicate). This ADR's core mechanism is that **the overseer authors a PR, on a branch, whose diff is exactly those audit files** — which #880 as written refuses to let the pre-PR gate open. Left unreconciled, the mechanism cannot produce a single audit PR. I bind the reconciliation:

- **Delete `_AUDIT_ONLY_FILES`.** The one audit-surface source is the AD-5 allowlist (Component B, `scripts/framework/audit_allowlist.txt`) plus the single glob helper AD-2 already mandates (the `require_human_approval.load_globs`/`glob_to_regex` style — no second glob dialect). `pre_pr_stale_check` reads from that source; it keeps **no** private copy.

Well-formedness, additions-only, and identity-binding are enforced downstream by the gate (Component C) and the bot (Component E); they are **not** `pre_pr_stale_check`'s job and must not be duplicated into it. `technical-design` chooses the exact factoring — a path-membership callable in `audit_predicate` that both rule 2 and Component H invoke, or a small shared helper both import — but it MUST be the **same** source and helper rule 2 uses, so the four copies collapse to one (the #1135 defence, extended to the fourth copy).

### AD-2 erratum — ESC-B (TD-VF-5): the refined `classify_audit_diff(files, allowlist)` signature is confirmed. (CONFIRMED — clarifying refinement, not a contract change.)

TD-VF-5's `classify_audit_diff(files: list[FileRecord], allowlist: list[str]) → AuditVerdict{qualifies: bool, reason: str}` is the correct, cleaner expression of AD-2's illustrative `(changed_paths, added_lines_by_path, existing_content_probe)`. The three illustrative inputs are not separate fetches — they are three projections of one trusted GitHub files-API record: `status == "added"` **is** the "existing-content probe" (first-creation, AF-2); `patch`/`additions` **is** `added_lines_by_path`; `filename` **is** `changed_paths`. The **shape** is right: it takes the changed files (as records) plus the allowlist, and returns whether the diff *qualifies* — where "qualifies" means every rule holds (non-empty diff; every path allowlisted; every `status ∈ {added, modified}`; every `deletions == 0`; every file with additions has a readable `patch`; every added line well-formed for its per-format validator) — with `reason` naming the first failing rule and the offending path. AD-2's illustrative signature is **superseded** by this one.

**One binding caveat (this is why it is an erratum, not a rubber stamp).** `FileRecord` must be the predicate's **own documented subset** (`filename`, `status`, `additions`, `deletions`, `patch`; unknown keys ignored) — **not** the raw `gh` response object. The projection from the `gh` files-API response into `FileRecord` happens in the **caller's** data-fetch helper (AF-1's trusted-base/data-only fetch), **outside** the pure function. This keeps `classify_audit_diff` network-agnostic and unit-testable with synthetic dicts (the only way the fail-closed branches get exercised), and — load-bearing — it means a future change to GitHub's response schema cannot silently alter qualification: the pure predicate only ever sees the frozen `FileRecord` contract. `technical-design`'s §3.1 already states this; I am binding it so it cannot be relaxed.

### AD-17 — Predicate/gate hardening bundle: five required rules; membership tightened. (Requirements BINDING; exact implementations routed to `technical-design`.)

- **(e) Patch-truncation MUST fail-closed.** If the files-API `patch` is truncated or absent for any file with `additions > 0`, the predicate returns `qualifies == False` (the parsed added-line count MUST be reconciled against the `additions` count; mismatch → reject).
